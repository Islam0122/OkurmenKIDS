## Introduction

This is OkurmenKIDS: a production education technology platform for a children's programming academy in Bishkek, Kyrgyzstan.

It is not a tutorial project. It is a live system used by trainers, assistants, managers, students and parents.

In this video, I'll walk through every production service, the backend behind them, and how it all is deployed.

## Platform Overview

OkurmenKIDS is one repository with four applications that share a single backend.

The public website lives at okurmenkids.com.

The learning management system is at lms.okurmenkids.com.

The Django administration panel is at api.okurmenkids.com, slash admin.

The Django REST API itself answers at api.okurmenkids.com.

And the exam training portal is at training.okurmenkids.com.

The three React frontends are deployed independently on Vercel, and all of them talk to one Django backend on Railway, backed by PostgreSQL.

## Public Website

The public website is the academy's front door: a React 19 and TypeScript single page application built with Vite.

It is available in Russian, Kyrgyz and English.

Courses, student projects, achievements, news, events and the team are not hard-coded. They come from the public site API and are managed by the marketing team inside the LMS.

When a parent books a trial lesson, the request is posted to the API as a lead.

## Learning Management System

The LMS is the operational core of the academy. Staff sign in, and access is role-based.

The backend defines roles such as trainer, team lead, assistant, accountant, director, operations, HR and marketing, plus one role for students and their parents.

Each role has its own cabinet: lessons, attendance, homework, exams, scholarships, salaries, recruitment and marketing.

Those cabinets hold private student data, so I'm only showing the public pages of the same application.

This is the public schedule: a read-only timetable by day, week, room and trainer, served from a cached public endpoint with a whitelist of fields.

Here is the gallery of student projects published by trainers, and the academy news feed.

The LMS is also an installable progressive web app with web push notifications.

## Django Administration

Next to the API runs the Django administration panel, themed with Jazzmin and a custom dashboard.

In production it sits behind a login, and I won't sign in on camera.

To show what it manages, this is the same admin running locally on an empty development database.

Accounting and payroll, the student and parent portal, marketing, news, operations, recruitment, testing, the website CMS and more. Every section comes from the backend's own Django apps, and access follows staff permissions.

## Backend REST API

The API host is api.okurmenkids.com. Its root path returns 404 by design: every route lives under api slash v1, and the health check returns status ok.

It is built with Django REST Framework and JWT authentication, and documented with an OpenAPI schema generated by drf-spectacular.

The production schema currently describes 724 paths and 966 operations, across 28 Django apps.

Academy, billing, accounting, testing, training, attendance, scholarships, recruitment, operations, marketing and the public website.

Public endpoints need no login, are throttled per IP address, and return only whitelisted fields.

## Training Portal

The training portal helps students prepare for exams. There is no registration: a student types only a name.

Tests come from the backend's testing module, with single choice, multiple choice, text and code questions, and an explanation for each answer.

The time limit and the grading are enforced on the server, not in the browser.

There are also curated videos, study materials and a leaderboard. The interface is in Kyrgyz, and every piece of content comes from the API.

## Technical Architecture

Here is the high-level architecture.

Three React and TypeScript frontends, the public website, the LMS and the training portal, are separate Vercel projects, so each one ships independently.

They all call one Django REST API on Railway, and the Django admin is served by the same backend.

The backend ships as a Docker image on Python 3.12 with Gunicorn and WhiteNoise. On start, it collects static files and applies migrations under a PostgreSQL advisory lock, so only one replica migrates.

Data lives in PostgreSQL, and uploaded media is stored on a Railway volume.

Background work is written as Celery tasks. Celery can use a Redis broker; without one, tasks run synchronously, and a Railway cron job runs the scheduled tasks every thirty minutes.

The backend also drives headless Chromium through Playwright to render report images for parents.

## Technology Stack

The stack: Python, Django and Django REST Framework. PostgreSQL. Celery, with Redis as an optional broker.

React, TypeScript and Vite on the frontend. Docker for the backend image, Railway for the backend, and Vercel for the three frontends.
