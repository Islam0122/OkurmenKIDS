# Оплата обучения: договоры по программам и учебные месяцы (`apps.billing`)

API: `/api/v1/accounting/billing/` · интерфейс: `/finance` (отдельный раздел
«Финансы» со своим sidebar; старый `/accounting/billing` перенаправляет туда)
· валюта: KGS · Celery: `config/celery.py`.

Оплата привязана к **учебным месяцам по фактически проведённым урокам
приоритетного предмета** (обычно IT), а не к календарю. Длина месяца (12
уроков IT), цена месяца, число месяцев и срок оплаты задаются программой
(тарифом) — в коде чисел нет. Тариф без продолжительности (`duration_months`
пуст) работает по-старому — бесконечные пакеты уроков со сроком по дате.

Демо-данные для ручной проверки (15 студентов-сценариев, демо-роли, очистка
только демо-набора): `python manage.py seed_billing_demo` — см.
[BILLING_DEMO.md](BILLING_DEMO.md).

## Договор по программе (с версии `billing/0002`)

| Понятие ТЗ | Где живёт |
|---|---|
| `ProgramBillingConfig` | `BillingPlan` (+ `duration_months`, `payment_deadline_lessons`, `allow_monthly`, `allow_full_prepay`, `currency`); `subject` — приоритетный предмет, `course` — программа LMS; цена месяца и уроков в месяце — в версиях `BillingPlanVersion` (история цен). Стандартная стоимость курса = цена месяца × месяцев |
| `StudentBillingContract` | `StudentBillingProfile` (+ снимок условий: `month_price`, `lessons_per_month`, `duration_months`, `deadline_lessons`, `standard_course_price`; `final_course_price`, `discount_enabled`, `discount_amount`, `payment_mode`, `reservation_allocation`; статус `COMPLETED` — курс пройден). `total_received` / `outstanding_balance` не хранятся — считаются из записей (`services.contracts.money_summary`) |
| `StudentStudyMonth` | `LessonPackage` (+ `month_number`, уникален в договоре среди не отменённых); `lessons_total` / `lessons_used` — требуется / зачтено уроков IT; `started_on` / `completed_on` — история переходов |
| `Invoice` | `Invoice` (+ `kind` MONTH/COURSE/PACKAGE, `due_lesson`, `due_reached_on`, `overdue_since`); одно действующее начисление на месяц |
| `Payment` | `accounting.StudentPayment` (+ назначение `prepayment`) |
| `PaymentAllocation` | `PaymentAllocation`; журнал авансов — `CreditLedgerEntry` |
| `Receipt` | новая модель `Receipt` (один чек на операцию, номер `OK-ГГГГ-NNNNNN`, снимок сумм) |
| `BillingAuditLog` | `accounting.PayrollAuditLog`, действия `billing_*` |
| настройки | новая модель `BillingSettings` (одна запись) |

**Учебный месяц — по приоритетному предмету.** С договора списываются только
уроки предмета договора (IT); English, Soft Skills и др. не списываются и не
задерживают переход. 12-й зачтённый урок IT завершает месяц №1, следующий
месяц начинается и (помесячно) выставляется начисление. Урок списывается
один раз (частичный уникальный индекс), отмена / перенос / исправление
посещаемости — сторно списания, прошлые начисления не меняются.

**Отображение месяца — единый расчёт** (`services/progress.py`,
`study_progress`): засчитанные ученику уроки 1–12 → месяц 1, 13–24 → месяц 2,
25–36 → месяц 3…; полные 12/12 остаются в завершённом месяце (на 12-м уроке —
«месяц 1 из 6, IT 12/12, курс 12/72», на 14-м — «месяц 2 из 6, IT 2/12, курс
14/72»). Используется строкой «Все студенты» / очередей / формы платежа
(`queues.contract_row`: `month_number`, `lessons_used`, `course_lessons_counted`,
`course_lessons_total`) и карточкой (`progress`, `months[].is_current`).
Платёжный цикл не меняется: на границе уже открыт пакет следующего месяца и
выставлено его начисление — это `billing_month_number` / `next_month_open`
(подсказка «выставлен месяц 2»). Засчитано ученику ≠ проведено занятий группы:
вкладка «Программы» академии показывает занятия группы, карточка — оба числа
(`progress.group_held`). Сверка на рабочей базе — `manage.py
billing_progress_audit` (только чтение).

**Срок оплаты — в уроках.** Начисление месяца должно быть оплачено не позднее
`deadline_lessons`-го (по умолчанию 3-го) зачтённого урока IT этого месяца:
1–2-й урок — «ожидается оплата», 3-й — «последний срок», с 4-го — просрочка
(`OVERDUE`, `overdue_since`). Дата наступления срока фиксируется
(`due_reached_on`) — по ней аналитика считает «ожидалось получить».

**Стоимость и скидка.** Скидка — не процент: при «Скидка предоставлена»
задаётся итоговая стоимость курса, скидка = стандартная − итоговая
(≥ 0, итоговая ≥ 0, причина обязательна). Начисление месяца k из N =
(итоговая − уже начислено) / (N − k + 1), округление вниз до тыйына, последний
месяц — точный остаток. Предоплата (`FULL_PREPAY`) — одно начисление
«Весь курс» на итоговую сумму в месяце 1 со сроком 3-го урока; месяцы 2…N
без начислений. Изменение тарифа не меняет оформленный договор; новая
итоговая цена в середине курса действует только на будущие месяцы.

**Бронь.** Один платёж с назначением «Бронь» — поэтому дважды вычесть его
нельзя (распределения платежа ≤ его суммы). `FIRST_MONTH` — сразу закрывает
часть месяца 1 (15 000 − 3 000 = доплата 12 000); `COURSE_TOTAL` — депозит
договора, автоматически закрывает только последний месяц (60 000 − 3 000 =
остаток 57 000). Бронь сама по себе не делает студента должником.

**Очереди бухгалтера** (`services/queues.py`): «К оплате» — выставленное и
не просроченное неоплаченное начисление; «Скоро оплата» — в текущем месяце
осталось ≤ `due_soon_lessons` уроков и следующий месяц не покрыт авансом;
«Просроченные» — есть `OVERDUE`. Строка показывает отдельно долг сейчас,
стоимость следующего месяца и свободный аванс.

**Аналитика** (`services/analytics.py`): «Фактически получено» — платежи по
дате поступления (валовые; возвраты отдельно; чистый поток = валовые −
возвраты; сторнированные не входят), «Ожидалось получить» — начисления, срок
которых наступил в периоде. Плюс разница, долг на конец периода (по
распределениям, действовавшим на дату), оплаченные / частичные / просроченные,
скидки, брони, предоплата, возвраты, разбивка по программам.

**Чек** (`services/receipts.py`, `receipt_pdf.py`): создаётся в транзакции
платежа / возврата / оплаты брони; снимок «уплачено ранее», «остаток долга по
договору», «доступный аванс»; HTML-страница `/finance/receipts/{id}` (CSS для
печати A4 и 80 мм) и PDF (`receipts/{id}/pdf/?size=a4|compact`, DejaVu —
кириллица, логотип `static/images/logo.png`). Повторная печать — только
счётчик и запись в журнале. Чек внутренний, не фискальный.

## Роли

| Роль | Может | Не может |
|---|---|---|
| Менеджер (`assistant`) | оформляет договор (программа, способ оплаты, итоговая стоимость / скидка — сверх лимита на согласование, бронь — ожидаемая сумма, особые условия), видит статусы оплаты («Все студенты», карточка без денежных операций) | вносить и менять платежи, видеть платежи / чеки / очереди / аналитику, менять настройки и историю (API — 403, сервис — `forbidden`) |
| Бухгалтер (`accountant`, группа `Accountant`) | всё в модуле: платежи, распределение авансов, начисления в рамках правил (корректировки, аннулирование не начатых), чеки, возвраты (лимит из настроек), сторно, контакты, тарифы и программы, согласование скидок, настройки | удалять финансовые записи (только корректирующие операции) |
| Директор (`director`, группа `BillingDirector` — только `view_*`) | только просмотр: Dashboard, очереди, студенты и статусы, платежи, чеки, аналитика, журнал | любые записи: `BillingAccess` отвечает 403 на любой не-GET запрос директора, сервисы — `forbidden` |
| Администратор системы (`admin`) | как бухгалтер (возврат сверх лимита — только он) | — |

**Изменение против прежних правил:** раньше директор был «администратором
оплаты» (тарифы, согласование скидок, корректировки). По ТЗ директор — только
просмотр, эти полномочия переданы бухгалтеру.

Проверки — в DRF (`BillingAccess`, `MoneyAccess`) и в каждом сервисе
(`permissions.authorize`). Системные события (урок проведён, статус
студента, Celery) идут с `actor=None` и могут только `SYSTEM_ACTIONS`.

Скидка менеджера: снижение итоговой стоимости курса (у тарифа без срока —
цены пакета) ≤ `BillingSettings.manager_max_discount_percent` % —
применяется сразу; больше — `BillingTermsChange(PENDING)`, уведомление
бухгалтеру, а
начисления профиля до решения — `DRAFT` (не требуют оплаты, деньги на них не
распределяются). Решение выставляет их (`OPEN`) по согласованным или
прежним условиям.

## Жизненный цикл

1. **Регистрация** (`create_student_billing_profile`) — профиль, условия,
   пакет №1 (`ACTIVE`) с начислением (срок — от даты начала обучения, если она
   впереди), бронь (если указана). Вручную ничего не начисляется.
2. **Урок проведён** — сигнал `post_save` урока → после коммита
   `lessons.sync_lesson`. Списывается со студента, если: урок «Проведён»;
   студент в этот день по истории LMS активен в этой группе; дата ≥ начала
   профиля и < остановки; предмет урока = направлению профиля (пустое
   направление — все уроки); правило отсутствия тарифа разрешает
   (`ALL_HELD` по умолчанию / `EXCEPT_EXCUSED` / `ATTENDED_ONLY`).
   Расписание (запланированный урок) ничего не списывает.
3. **Защита от двойного списания** — блокировка профиля + частичный
   уникальный индекс `unique_active_lesson_consumption (profile, lesson_ref)`.
4. **Ошибочное списание** — сторно (`reverse_consumption`): исходное
   `REVERSED`, новая запись `REVERSAL`. Урок отменили / удалили / отсутствие
   стало уважительным — `sync_lesson` сторнирует сам. Сторно в уже
   использованном пакете освобождает в нём место: следующий урок займёт его,
   нового начисления нет.
5. **Пакет скоро закончится** — уведомление за `warn_before_end_lessons`
   уроков (12 и 3 → после 9-го), один раз на пакет.
6. **Раннее начисление** — только при `early_invoice_enabled` и
   `early_invoice_after_lessons` (например 9 из 12): создаётся следующий пакет
   `PLANNED` с начислением.
7. **Пакет использован** (`complete_package`) → следующий цикл
   (`create_next_package_invoice`, под блокировкой профиля): есть
   `PLANNED` (оплачен вперёд / выставлен заранее) — он становится текущим,
   **нового начисления нет**; иначе, если студент продолжает обучение
   (профиль `ACTIVE` и студент `active`), — новый пакет по действующим
   условиям (снимок), аванс применяется сразу (покрыл всё — `PAID`; часть —
   остаток на том же начислении), срок — `payment_due_days`, задача
   ответственному бухгалтеру, уведомление после коммита. Дата начисления —
   дата урока, завершившего пакет.
8. **Пауза** — новые пакеты не выставляются; возврат — профиль снова
   активен. **Деактивация / завершение обучения** — начисления остановлены с
   даты события; старые начисления и долги остаются; не начатые будущие
   пакеты отменяются, их оплата сторнируется в аванс (возврат — решением
   бухгалтера). **Перевод в группу** — пакет и долг остаются, уроки новой
   группы с даты перевода списываются в тот же пакет.

## Деньги

* Поступление (`record_payment`) — `StudentPayment` + `CreditLedgerEntry
  PAYMENT_IN` на всю сумму. Распределение на начисление —
  `PaymentAllocation` + `CreditLedgerEntry ALLOCATION` (−). Аванс = Σ журнала;
  нераспределённое по платежу = Σ записей платежа. Одни и те же деньги не
  могут быть и оплатой начисления, и свободным авансом.
* **Остаток начисления** = сумма − действующие распределения − применённые
  корректировки (`calculate_invoice_balance`; поля `amount_paid` /
  `amount_adjusted` — кеш под блокировкой, сверка — `billing_reconcile`).
* Статусы: `DRAFT`, `OPEN`, `PARTIALLY_PAID`, `PAID`, `OVERDUE` (срок прошёл и
  есть остаток — ставит задача `mark_overdue_invoices`), `VOID`.
* Сценарии: A — 4000/4000 → `PAID`; B — 4000/2500 → остаток 1500,
  `PARTIALLY_PAID`; C — `prepay_packages=N` создаёт N следующих пакетов с
  начислениями и распределяет по ним деньги, остаток — аванс; D — бронь →
  аванс, применяется при платёжном событии (новое начисление, наступил срок,
  решение бухгалтера `apply-credit`).
* Сумма платежа никогда не меняется. Исправления: сторно распределения
  (деньги в аванс), сторно платежа (все распределения сторнируются, платёж
  `void` с причиной), возврат (`refund`, только из нераспределённого
  остатка), отмена возврата, корректировка начисления, аннулирование не
  начатого начисления. Старый `student-payments/{id}/void/` для платежа по
  пакетам вызывает то же сторно; возврат через старый эндпоинт запрещён.
* Идемпотентность: `Idempotency-Key` (или `idempotency_key`) — повтор
  возвращает тот же платёж (200), другой платёж с тем же ключом — 400;
  номер документа не принимается дважды для профиля.
* Блокировки: каждая денежная операция — `transaction.atomic()` +
  `select_for_update` профиля (параллельные платежи, сторно и возвраты одного
  студента выполняются по очереди), уникальные индексы — последняя защита.

## Периоды: три даты (с версии `billing/0004`)

Сентябрьские данные остаются сентябрьскими, даже если сейчас октябрь:

| Дата | Поле | Что определяет |
|---|---|---|
| Период начисления | `Invoice.period_date` | к какому учебному / финансовому месяцу относится долг |
| Дата поступления | `StudentPayment.received_date` | к какому месяцу относятся полученные деньги |
| Дата корректировки | `InvoiceAdjustment.effective_date` | с какой даты долг уменьшен корректировкой |
| Дата записи | `created_at` (все модели) | только аудит; в отчётах — признак «внесено задним числом» |

* **Причина прежней привязки к октябрю:** при оформлении договора первое
  начисление получало дату «сегодня» (`create_first_package(on_date=localdate())`),
  отчёт «начислено» считался по этой дате, деньги при зачислении проводились
  только сегодняшним днём, а «долг на дату» — по времени записи
  распределения, а не по дате денег. Договор с 1 сентября, внесённый 24
  октября, становился октябрьским.
* Период начисления: первый месяц — дата начала договора (`start_date`);
  следующие — дата урока IT, которым закончился предыдущий учебный месяц
  (переход определяют уроки, а не календарь); перевыставление при смене
  способа оплаты — период прежнего начисления; фоновое восстановление
  пропущенного цикла — дата завершения предыдущего месяца. `issue_date` —
  дата выставления (от неё срок оплаты), `created_at` — время записи.
* Период фиксируется при создании; редактирование посещаемости, перевод в
  другую группу, изменение условий его не меняют. Исправление — только
  `POST invoices/{id}/period/` (`period_date`, `reason`; администратор оплаты),
  с записью `billing_invoice_period` в журнале аудита.
* Платёж: `received_date` — фактическая дата денег, можно прошлую (не
  будущую). Деньги, полученные в октябре, могут гасить сентябрьский долг
  (FIFO или выбранное начисление) — долг сентября уменьшается, но поступление
  остаётся октябрьским («за прошлые периоды»).
* Историческая задолженность на дату = начисления периодов до даты − оплаты
  деньгами, полученными до этой даты, − корректировки с датой до неё.
  Сторнированные распределения и отменённые корректировки (исправленные
  ошибки) не учитываются ни в какую дату.
* `GET periods/` — месяцы для переключателя; `GET reports/period/?month=2026-09`
  (или `date_from` + `date_to`, фильтры `group`, `subject`, `student`,
  `accountant`, `plan`): поступило в периоде и за какие периоды (текущий /
  прошлые по месяцам / будущие / аванс, сколько внесено задним числом);
  начислено за период и его судьба (оплачено заранее / в периоде / позже по
  месяцам поступления / не оплачено на конец и сейчас); долг на начало и на
  конец; должники на конец периода.
* Интерфейс: переключатель «Финансовый период» (месяцы и произвольный
  диапазон) над всеми денежными страницами — Dashboard, Платежи (по дате
  поступления), Аналитика; «Добавить платёж» — дата фактического получения и
  назначение, у начислений виден их период.

## Показатели карточки и отчётов (единые формулы)

Источник — `contracts.money_summary` (карточка, очереди, чек, предпросмотр
платежа); отчёты за период — `periods.period_report`, «Ожидалось» —
`analytics.finance_analytics`, «Долг сейчас» на Dashboard — `reports.dashboard`,
«Остаток предоплаты за обучение» — `prepayments.prepayments` (см. ниже). Frontend ничего не пересчитывает.

| Показатель | Поле | Формула |
|---|---|---|
| Получено по договору | `net_received` | Σ подтверждённых платежей − Σ подтверждённых возвратов (сторнированные не входят) |
| Оплачено по начислениям | `allocated` | Σ действующих `PaymentAllocation` |
| Свободный аванс | `credit` | Σ `CreditLedgerEntry` = получено − возвраты − распределено − удержания брони |
| Начислено | `invoiced` | Σ действующих (не VOID) начислений |
| Остаток начисления | `Invoice.balance` | сумма − действующие распределения − применённые корректировки (≥ 0, ограничение БД) |
| Остаток начислений | `invoices_balance` | Σ остатков неоплаченных начислений |
| Применимый аванс | `credit_applicable` | аванс, который правила договора разрешают направить на эти начисления (бронь «в общую стоимость» — только «Весь курс» / последний месяц) |
| К оплате сейчас | `due_now` | max(остаток начислений − применимый аванс, 0) |
| Просрочено | `overdue` | max(остаток просроченных − применимый аванс, 0) |
| Остаток по договору | `outstanding` | max(итоговая − распределено − аванс − корректировки, 0) |
| Будущие обязательства | `future` | max(итоговая − начислено, 0) — не долг и не просрочка |
| Несогласованность | `credit_unapplied` | min(применимый аванс, остаток начислений) — должно быть 0 |

### Остаток предоплаты за обучение (`services/prepayments.py`, `GET prepayments/`)

Карточка Dashboard (`prepayment_total`) и страница `/finance/prepayments`
считаются одной функцией: итог карточки = Σ строк детализации. Раньше
карточка «Свободные авансы» показывала технический `credit_total` = Σ
`CreditLedgerEntry` по всем договорам: туда попадали закрытые договоры,
не зачтённый депозит брони «в общую стоимость», аванс рядом с неоплаченным
начислением, а полная предоплата курса (уже распределённая на «Весь курс»)
не попадала вовсе. `credit_total` оставлен в ответе как технический показатель.

| Показатель | Поле | Формула |
|---|---|---|
| Не распределено по счетам | `unallocated` | max(`credit` − не зачтённый депозит брони «в общую стоимость», 0) |
| Распределено на будущие месяцы | `allocated_future` | действующие распределения на начисления не начатых пакетов (PLANNED, 0 уроков) + доля оплаченного «Весь курс» на не начатые месяцы (по плану месяцев; без плана — равными долями, `allocated_future_exact=false`) |
| Остаток предоплаты | `prepayment` | `unallocated` + `allocated_future` (одна сумма не входит в оба) |
| Зачтено в обучение | `applied_to_studied` | `allocated` − `allocated_future` |
| Оставшаяся стоимость | `remaining_obligations` | остаток начислений + будущие обязательства + `allocated_future` |

Статус: «Требует проверки» — договор закрыт, `credit_unapplied` > 0,
отрицательный аванс или график не сходится с ценой; иначе «Остаток аванса» —
итоговой цены нет или обязательств не осталось; «Полная предоплата» —
`prepayment` ≥ `remaining_obligations`; иначе «Частичная предоплата».
Размер отдельного платежа не учитывается. Фильтры: группа, предмет,
программа (`program`), статус, поиск по имени; доступ — `MoneyAccess`.

Отчёт за период: долг на конец = долг на начало + начислено за период −
оплачено (деньгами, полученными до конца периода) − корректировки до конца
периода; «погашено позже» — распределения на начисления периода из платежей,
полученных после его конца (по месяцам поступления).

**Регистрация платежа** (`payments.record_payment`, одна транзакция под
блокировкой договора, `Idempotency-Key`): платёж → весь в аванс (ledger) →
выбранное начисление (если указано) → остальные неоплаченные по порядку
(`may_fund`) → остаток — свободный аванс → статусы начислений → чек → аудит;
уведомления — после коммита. «Предоплата / аванс» больше не оставляет деньги
авансом рядом с выставленным начислением (раньше `auto_allocate=False`:
одна сумма была одновременно «к оплате» и «свободным авансом»).
`auto_allocate=False` в сервисе — только явное решение держать деньги до
платёжного события.

**Предоплата курса:** одно начисление «Весь курс» на итоговую стоимость —
обязательство договора, а не стоимость месяца №1 (к пакету №1 оно привязано
только технически, срок — 3-й урок первого месяца); месяцы 2…N — пакеты без
начисления (`month_charge` = итоговая − уже начислено = 0). Повторные запуски
уроков и фоновых задач начислений не добавляют.

* `contracts.course_month_shares` — доля «Весь курс» на каждый месяц: по плану
  стоимости месяцев (если он сходится с суммой), иначе поровну (53 000 / 4 =
  13 250). Это разбивка одного начисления, не новые начисления.
* `contracts.course_coverage` — сколько каждой доли закрыто оплатой «Весь курс»
  (деньги идут на месяцы по порядку).
* График (`payment_schedule`): `course` — само начисление (сумма, оплачено,
  остаток, `paid_in_full`); строки месяцев — `state` `prepaid` (доля оплачена)
  или `course_due` (ждёт оплаты курса), `kind = COURSE`, `to_pay` и `balance`
  = 0 — долг считается один раз, у начисления курса. После повышения цены —
  одна строка доплаты (`future`) в первом ещё не созданном месяце, её выставит
  `month_charge`.
* Карточка: месяц показывает `course_share` вместо начисления «Весь курс».
* «Скоро оплата» (`next_month_cost`): стоимость следующего месяца — его доля
  курса, `prepaid` — оплаченная часть, к оплате — только доплата сверх курса.
* `money_summary.course_paid_in_full` — итоговая покрыта, долга нет: карточка
  пишет «Курс полностью оплачен». Кнопка «Добавить платёж» остаётся у всех,
  кто принимает платежи; добровольная сумма при нулевом долге становится
  авансом (предпросмотр — `course_paid_in_full`), начисления и статус «Весь
  курс» не меняются.

**Учёт уроков:** `profiles/{id}/lessons/` — каждое посещение с предметом,
группой, отметкой, датой договора и причиной («Засчитан», «Другой предмет»,
«У урока не указан предмет», «Урок отменён», «Урок не подтверждён», «До даты
начала договора», «После остановки», «Студент не числился в группе…»).
Ошибочная дата начала — `POST profiles/{id}/start-date/` (`start_date`,
`reason`; администратор оплаты, аудит `billing_profile_start_date`): уроки
приоритетного предмета с новой даты засчитываются по обычным правилам, период
первого начисления переносится, посещаемость и деньги не меняются; сдвиг позже
уже засчитанных уроков запрещён.

**Аудит и исправление данных** — `manage.py billing_money_audit` (по
умолчанию только чтение): `--receipt`, `--invoice`, `--student`, `--profile`;
все платежи, чеки, начисления (включая аннулированные), распределения
(включая сторнированные), журнал аванса, проблемы. `--apply --confirm` —
распределить свободный аванс (`credit_unapplied`); `--reverse-payment ID
--reason … --confirm` — сторно платежа, признанного повторной регистрацией
(платёж «Отменён», чек «Аннулирован», ничего не удаляется). Одинаковые суммы
(`same_amount_payments`, `possible_duplicate_payment`) не объединяются
автоматически — их подтверждает бухгалтер по кассе / выписке. Ежедневная
сверка (`reconcile`) сообщает `credit_unapplied`.

## Управление платежами (исправление, аннулирование, чек, история)

Платёж не редактируется формой модели: каждое действие — сервис
`services/corrections.py` (или `payments.reverse_payment`) в одной
транзакции под блокировкой договора(ов) и платежа, с причиной и записью в
журнале аудита (кто, когда, что было, что стало, чек, распределения).

**Где:** бухгалтер — «Финансы → Платежи → строка платежа» (`/finance/payments/:id`);
администратор системы — Django Admin «Платежи студентов → Открыть / исправить
/ аннулировать» (`/admin/accounting/studentpayment/<id>/manage/`). Директор и
бухгалтер — роли только LMS, в Django Admin не входят; директор видит платёж,
чек и историю без кнопок изменений.

| Действие | API | Что происходит |
|---|---|---|
| Исправить дату поступления | `POST payments/{id}/correct/` `{received_date, reason}` | отчёты по поступлениям — по новой дате; период начисления не меняется; номер чека прежний, в снимке чека новая дата, старый снимок — в `snapshot.history` |
| Сумма | `{amount, reason[, allocations]}` | разница — запись журнала аванса `PAYMENT_ADJUST`; уменьшение ниже распределённого — только с новым распределением; чек перевыпускается (`OK-…/1`) |
| Способ, документ, комментарий, назначение | `{method / reference / comment / purpose, reason}` | бронь меняется только через бронь |
| Другой студент / договор | `{profile, reason}` | распределения сторнируются, деньги переходят записями `PAYMENT_ADJUST`, распределяются по новому договору; чек перевыпускается |
| Распределение | `{allocations: [{invoice, amount}], reason}` | действующие распределения платежа сторнируются, создаются указанные; остаток — аванс |
| Дата создания записи | `POST payments/{id}/created-at/` | отдельная административная корректировка (отчёты её не используют) |
| Аннулировать | `POST payments/{id}/reverse/` `{reason}` | распределения сторнируются (долг возвращается), платёж «Отменён», чек «Аннулирован»; повторно — 400 |
| История | `GET payments/{id}/history/` | журнал по платежу, чеку и распределениям (только чтение) |
| Чек | `receipts/{id}/`, `receipts/{id}/pdf/`, `POST receipts/{id}/printed/` | повторная печать — только счётчик, без новых записей |

Поиск и фильтры: `payments/?number=` (№ платежа или чека), `month=ГГГГ-ММ`
(месяц поступления), `student`, `method`, `status`, `date_from` / `date_to`.

Правила: причина обязательна; повтор той же формы ничего не меняет (нет
изменений — нет записи); будущая дата поступления запрещена; если старая или
новая дата попадает в утверждённый / закрытый расчётный период бухгалтерии
(`PayrollPeriod` APPROVED / CLOSED), нужно явное подтверждение
(`confirm_closed_period`), предупреждение сохраняется в журнале. Физическое
удаление платежей модель не допускает (`ImmutableQuerySet`): ошибочный
платёж аннулируется, история остаётся. Журнал аудита не изменяется и не
удаляется. Менеджер платежи не видит и не меняет (как и раньше —
`MoneyAccess`).

**Инструкция бухгалтеру — «платёж записан 24.10, деньги получены 08.09»:**
Финансы → Платежи → найти по № чека → открыть → «Исправить дату» → 08.09.2026 →
причина → «Сохранить». Платёж и номер чека прежние; поступление переходит в
сентябрьский отчёт; начисление остаётся в своём периоде; в «Истории
изменений» видно старую и новую дату.

## Сторно, заменяющие платежи и аванс на будущие начисления (с версии `billing/0008`)

* Сторно (`reverse_payment`) отменяет запись в учёте: распределения
  сторнируются, чек аннулирован, в «получено» платёж не входит. Это не
  возврат денег родителю (возврат — `refund_payment`). Карточка показывает
  сторнированные суммы отдельно (`voided`, «не учитывается»).
* Разделить один платёж на начисления и аванс — исправлением распределения
  того же платежа (`correct_payment allocations=…`): новых поступлений и
  чеков нет. Если деньги всё же внесены заново после сторно, связь
  `PaymentReplacement` (исходный VOID → заменяющие) делает цепочку видимой:
  `record_payment(replaces=…)` / поле «Взамен сторнированного платежа» в
  «Добавить платёж»; сумма заменяющих ≤ исходного; один платёж заменяет
  только один. Для старых записей: `billing_money_audit` сообщает
  `unlinked_replacement` (кандидаты), связь —
  `--link ID --replacements A,B --reason … [--confirm]` (dry-run, идемпотентно,
  аудит `billing_payment_replacement`; деньги не меняются).
* Аванс: `credit` — реально нераспределённые деньги; из них
  `credit_reserved_future` — прогноз, какая часть закроет будущие (ещё не
  выставленные) месяцы; `credit_unreserved` — сверх договора; `net_to_pay` —
  осталось оплатить. Распределение на будущий месяц происходит только при его
  выставлении. В графике колонка «Закроет аванс (прогноз)».
* Повторное сохранение той же стоимости курса / тех же условий не создаёт
  запись `BillingTermsChange` (API отвечает `changed: false`). Старые записи
  «38 000 → 38 000» не удаляются, но в истории стоимости не показываются.

## Django Admin → «Удалить профиль из бухгалтерии» (ошибочно созданный профиль)

«Платёжные профили студентов» → отметить профиль → действие «Удалить профиль
из бухгалтерии» → страница `…/studentbillingprofile/<id>/purge/` с
предупреждением, списком типов записей и платежами профиля → причина и
фамилия ученика → удаление (`services/profile_purge.py`).

* **Доступ — только суперпользователь Django** (`is_superuser`, активный).
  Проверяется независимо в `get_actions` (действие не показывается), в самом
  действии, в представлении (403 на GET и POST) и в сервисе. Разрешения, роль
  бухгалтера / директора и `is_staff` доступа не дают.
* **Что удаляется** — найдено по внешним ключам от профиля: цены месяцев,
  история условий, учебные месяцы и списания уроков в них, начисления и
  корректировки, распределения, журнал аванса, брони, платежи профиля и
  возвраты, чеки, связи «взамен», задачи, контакты, уведомления, строки
  реестра демо-данных. Тариф не удаляется.
* **Не удаляется** — ученик, группа, расписание, уроки, посещаемость, оценки и
  всё вне `billing` / `accounting`: на эти записи ничто вне бухгалтерии не
  ссылается, количество записей всех остальных таблиц сверяется до и после.
* **Остановка** — проведённый платёж или возврат (обычный режим), связь с
  записью другого профиля, изменение данных после просмотра отчёта.
* **Полный сброс** (если мешают только проведённые платежи профиля) — удаляет
  и их с чеками. Отчёт показывает каждый платёж (сумма, дата денег, чек, кто
  внёс, «возможен повторный ввод»); подтверждение — причина, фамилия, фраза
  «СБРОСИТЬ БУХГАЛТЕРИЮ», отметка «понимаю, что суммы уйдут из отчётов о
  поступлениях», для утверждённого / закрытого периода — отдельная отметка.
  Сервис удаляет ровно показанные платежи (новый платёж после просмотра —
  отказ). Сторно, возвраты и платежи «взамен» не создаются: реально
  полученные деньги вносятся в новый профиль обычной оплатой.
* **История** — полная копия удалённых строк в `PayrollAuditLog`
  (`billing_profile_purge`), журнал аудита не удаляется. После удаления можно
  сразу оформить новый профиль: уроки с даты начала спишутся в него.

## Django Admin → «Неправильные данные» (исправление финансовых записей)

Пункт меню раздела «Оплата обучения» (прокси `FinancialCorrection`,
`/admin/billing/financialcorrection/`). Виден и работает только с
разрешением `billing.correct_financial_records` («Исправление неправильных
финансовых данных», миграция `0007`; суперпользователь — все права).
Разрешение проверяется в каждом представлении (в т.ч. прямой POST), а сами
изменения выполняют сервисы со своей проверкой роли (администратор оплаты),
блокировками и аудитом. Бухгалтер, менеджер, директор — роли LMS, в Django
Admin не входят.

* Поиск: студент, № платежа / чека / начисления, дата поступления, период
  начисления, сумма, статус; результаты — платежи, начисления, брони.
* Исправление в два шага: форма → «было / станет», причина, предупреждение о
  влиянии на долг, аванс и отчёты → «Сохранить исправление» / «Отмена».
  Открытие формы и проверка ничего не меняют.
  * Платёж (`corrections.correct_payment`): дата поступления, сумма, способ,
    договор / студент, назначение, распределение, комментарий.
  * Начисление (`record_corrections`): сумма (не ниже оплаченного), срок
    (дата или урок №), период, примечание (`snapshot.note`), перенос на
    другой договор (только без оплат, корректировок и уроков: аннулируется и
    выставляется заново).
  * Бронь: сумма и срок (неоплаченная), дата и сумма оплаты (это платёж),
    перенос на другой договор вместе с платежом, условие зачёта брони.
* «Аннулировать ошибочную операцию»: платёж — сторно (чек аннулирован),
  начисление — VOID, бронь — отмена (оплаченная — со сторно платежа).
  Повторно — ошибка; ничего не удаляется.
* Журнал исправлений (`…/journal/`, только чтение): `admin_financial_correction`
  (кто, когда, тип, было / стало, причина, связанные платёж / чек /
  начисления) и записи сервисов.

## Индивидуальная стоимость учебных месяцев (с версии `billing/0006`)

Модель `ContractMonthPrice` (договор, месяц №, `standard_price`, `amount`) и
поле договора `month_plan_mode`: пусто — прежнее правило (итоговая поровну на
оставшиеся месяцы, все существующие договоры), `PROPORTIONAL` — скидка
пропорционально стандартным ценам месяцев, `MANUAL` — итоговая сумма месяца
вручную. Стандартная стоимость договора = Σ стандартных цен (13 000 + 15 000
× 3 = 58 000), скидка = стандартная − итоговая.

* Распределение — `services/month_plan.py`: пропорционально с округлением
  вниз до тыйына, остаток тыйынов — месяцам с наибольшей дробной частью;
  Σ месяцев = итоговая ровно (58 000 → 50 000: 11 206,90 + 12 931,04 +
  12 931,03 + 12 931,03). Вручную — Σ обязана совпасть, иначе ошибка с разницей.
* `month_charge` берёт сумму месяца из плана (не больше остатка итоговой);
  начисление — снимок, план выставленных месяцев равен их начислению.
  Изменение плана распределяет остаток только по не выставленным месяцам;
  выставленные меняются отдельно: «перевыставить не начатые» (без уроков и
  корректировок; оплата возвращается в аванс и применяется снова, бронь не
  удваивается) или корректировка начисления.
* Предоплата курса: одно начисление «Весь курс» = итоговая, план — разбивка
  по месяцам.
* Изменение итоговой обычным «Стоимость курса»: PROPORTIONAL — оставшиеся
  месяцы пересчитываются; MANUAL — запрещено, меняйте план.
* Права: план меняет бухгалтер (администратор оплаты) с причиной и аудитом
  (`billing_month_plan`); менеджер при оформлении может задать цены месяцев
  только с пропорциональной скидкой; директор — просмотр.
* API: `profiles` POST — `month_prices`, `month_plan_mode`, `month_amounts`;
  `GET/POST profiles/{id}/month-plan/` (`standard_prices`,
  `final_course_price`, `mode`, `manual_amounts`, `reason`,
  `reissue_unstarted`, `dry_run`). Повторное сохранение того же плана —
  без изменений и без новых начислений.
* Django Admin: «Платёжные профили» — стандартная, итоговая, скидка, правило;
  строка договора → «План месяцев» (предпросмотр, сохранение, план начислений).
* Отчёт: `manage.py billing_month_plan_report [--all]` — договоры, у которых
  начисления + прогноз или сумма плана ≠ итоговой (только чтение).

## Бронь — это платёж, а не вторые деньги

Оплаченная бронь (`Reservation.status=PAID`) ссылается на свой платёж
(`Reservation.payment`, `StudentPayment.purpose=reservation`). В «Получено
по договору» считается только платёж — один раз. Деньги брони, как любой
платёж, распределяются на начисления (режим «в первый месяц» — без
ограничений, сначала месяц 1, затем следующие; режим «в общую стоимость» —
только «Весь курс» / последний месяц), остаток — свободный аванс
(`reservation_unused`). Карточка показывает у брони: платёж №, дата, чек,
«засчитано в начисления», «осталось авансом».

* Деньги внесены через «Оплату брони», а это оплата обучения (например,
  весь курс): `POST payments/{id}/correct/ {purpose: tuition|prepayment,
  reason}` — бронь закрывается без возврата и удержания, деньги и их
  распределения не меняются, ограничения брони снимаются (аудит
  `billing_reservation_reclassify`).
* Аннулирование платежа брони: распределения сторнируются, бронь снова
  «ожидает оплаты» (её можно отменить), чек аннулирован.
* Неоплаченная бронь: `POST reservations/{id}/edit/` (сумма, срок, причина);
  отмена — `reservations/{id}/cancel/`. Дата и сумма оплаченной брони — это
  платёж: исправляются формой платежа.
* `billing_money_audit` сообщает `reservation_paid_over_expected` (принято
  больше суммы брони — проверьте назначение) и `schedule_mismatch`.

**График оплаты** (`contracts.payment_schedule`, в карточке — «График оплаты
по договору»): выставленные месяцы + прогноз оставшихся по формуле
`month_charge`, сколько закроет аванс и сколько останется оплатить;
проверка Σ начислений + Σ прогноза = итоговая стоимость; история изменений
итоговой стоимости. Если итоговая изменилась после выставления месяцев,
выставленные суммы не пересчитываются (снимок), разница уходит в оставшиеся
месяцы (пример: 40 000 → месяцы 1–2 по 10 000; итоговая 38 000 → месяцы 3–4
по 9 000).

**«Платежи и чеки»** в карточке: одна операция — одна строка (Дата, Тип
операции: платёж / бронь / предоплата / возврат, Сумма, Способ, Статус
(проведён / сторно), Кто принял, Номер чека, Действия: открыть, сторно); на
телефоне — карточка на операцию.

## Бронь (операции)

Менеджер оформляет (`PENDING`, ожидаемая сумма) → бухгалтер регистрирует
фактически полученную сумму (`reservations/{id}/pay/`, платёж с `purpose
= reservation`) — это аванс, не оплата пакета → при отмене
(`reservations/{id}/cancel/`) неиспользованная часть возвращается
(`refund_amount`) и/или удерживается (`retain_amount`, запись `RETENTION`) с
основанием; остальное остаётся авансом.

## Студенты и подключение к оплате

Вкладка «Студенты» (открывается первой) показывает **всех активных
студентов LMS**: подключённых — с направлением, тарифом, пакетом
(«№2: 9 из 12»), долгом, авансом, сроком и статусом оплаты; остальных — с
пометкой «Не подключён к оплате». Менеджер, директор и администратор
отмечают студентов (или берут группу / всех) и подключают их к тарифу
одной кнопкой; уже подключённые к этому направлению пропускаются. Если
тарифов ещё нет, директор / администратор создаёт тариф там же.

## Работа бухгалтера

* **Задача** (`BillingTask`) создаётся на каждое неоплаченное начисление,
  назначается ответственному бухгалтеру профиля, закрывается автоматически,
  когда начисление оплачено (`DONE`) или аннулировано (`CANCELLED`).
* **Журнал контактов** (`contacts/`) — только добавление; канал (звонок,
  Telegram, WhatsApp, другое), результат (ответил, не ответил, обещал оплатить
  — дата обязательна, оплата получена, спор, повторный контакт — дата
  следующего контакта обязательна), комментарий. Контакт обновляет задачу
  (обещанная дата, следующий контакт, «спор»). Запись «оплата получена» без
  денег задачу не закрывает.
* **Панель** (`dashboard/`, страница «Оплата обучения»): студенты ожидают
  оплаты (уникальные), начисления к оплате (счета), общий долг, просрочки
  (счета / студенты / сумма), скоро срок (`BILLING_DUE_SOON_DAYS`),
  поступления и возвраты за период, авансы, частичная оплата, открытые
  задачи, контакты. Фильтры: `group`, `subject`, `student`, `status`,
  `date_from`/`date_to`, `accountant` (+ `plan`). Активные студенты — отдельный
  показатель.
* **Должники** (`debts/`) — по студенту: счетов, долг, просрочено, дней
  просрочки, обещание, следующий и последний контакт, аванс.
* **Отчёт** (`reports/summary/`) — начислено, поступило, возвращено, нетто,
  долг и аванс на сейчас, по направлениям.

## Фоновые задачи (`apps/billing/tasks.py`)

| Задача | Что делает |
|---|---|
| `billing.process_completed_lessons` | пересинхронизация уроков за `BILLING_SYNC_LOOKBACK_DAYS` (подстраховка сигналов) |
| `billing.process_completed_packages` | использованный пакет без следующего у продолжающего студента → следующий цикл |
| `billing.create_early_invoices` | раннее начисление по настройке тарифа |
| `billing.check_packages_ending` | предупреждение о конце пакета |
| `billing.apply_credit_to_due_invoices` | аванс → начисления, срок которых наступил |
| `billing.mark_overdue_invoices` | просрочки + уведомления |
| `billing.follow_up_contacts` | повторные контакты, невыполненные обещания |
| `billing.notify_accountants` | доставка уведомлений outbox |
| `billing.build_financial_report` | снимок отчёта месяца и сверка (в `BillingEvent.result`) |
| `billing.run_daily` | всё по порядку |

Beat (`CELERY_BEAT_SCHEDULE`) только запускает проверки; повторный запуск
безопасен — блокировки профиля, бизнес-ключи (`profile+number` пакета, одно
действующее начисление на пакет, `business_key`, `dedup_key` уведомлений),
`autoretry` с backoff. Каждый запуск пишется в `BillingEvent` (ключ задачи и
дня, попытки, результат / ошибка). Уведомления — transactional outbox:
создаются в транзакции события, доставляются `on_commit` и задачей.

Без брокера (`CELERY_BROKER_URL` пуст) задачи выполняются синхронно; для
хостинга без Redis — `python manage.py billing_autorun` (cron, раз в день или
чаще). Для Redis нужен пакет `redis` и `CELERY_BROKER_URL=redis://…`:

```
celery -A config worker -l info
celery -A config beat -l info
```

## Миграции и существующие данные

```
python manage.py billing_migration_report > before.json   # количества и суммы до
python manage.py migrate        # accounting 0014 (назначение «Предоплата»), billing 0002 (поля договора,
                                # Receipt, BillingSettings, ограничения), billing 0003 (чеки для старых платежей)
python manage.py billing_migration_report > after.json    # должны совпасть (кроме receipts)
python manage.py billing_reconcile                         # сверка, код 1 при расхождениях
```

Mapping: старые профили, пакеты, начисления, платежи, распределения и брони
остаются как есть (новые поля — со значениями по умолчанию: `kind=PACKAGE`,
`due_lesson` пусто → срок по дате). `billing/0003` создаёт только чеки для уже
зарегистрированных платежей (без новых платежей и пересчётов; повторный запуск
ничего не дублирует, отменённый платёж — чек «Аннулирован»). Профили без
программы с продолжительностью перечислены в `billing_migration_report`
(`legacy_profiles_without_program`) — их переводит бухгалтер, оформив новый
договор по программе (старый — «Остановить начисления»). Фиктивные платежи
для выравнивания баланса не создаются.

Миграции только добавляют таблицы, поля и ограничения; существующие
`StudentPayment` не меняются (у них период обучения заполнен — новые
ограничения выполняются). Профили оплаты для уже учащихся студентов
автоматически не создаются: старые платежи не привязаны к пакетам, и
угадывать, сколько уроков уже оплачено, нельзя — менеджер регистрирует
профиль (дата начала = с какого урока считать пакет), а аванс за ранее
оплаченное бухгалтер вносит платежом с комментарием.

`billing/0004` (периоды) добавляет `Invoice.period_date` и
`InvoiceAdjustment.effective_date` и заполняет их без изменения смысла:
период = `issue_date`, дата корректировки = день её создания. Ни одна сумма,
статус или прежняя дата не меняется (`billing_migration_report` до и после
совпадает). Начисления, период которых, вероятно, записан днём оформления
договора, а не его началом, автоматически не исправляются:

```
python manage.py billing_period_review            # список: with_basis и manual_review (ничего не меняет)
python manage.py billing_period_review --apply    # исправить только строки с основанием, с аудитом
```

Основание — начало договора и первый засчитанный урок пакета в одном месяце.
Без уроков или если месяцы расходятся — `manual_review`: бухгалтер проверяет
и исправляет через `POST invoices/{id}/period/` с основанием.

Обслуживающая очистка бухгалтерии (режим B, удаление `studentpayment`) при
наличии данных оплаты обучения откатится (`PROTECT`) — данные billing она не
удаляет.

## Нерешённые вопросы (нужно решение руководства)

0. **Новое (договоры по программам):** стандартная стоимость курса = цена
   месяца × месяцев (цена, не делящаяся на месяцы, задаётся итоговой
   стоимостью со скидкой); бронь «в общую стоимость» закрывает последний
   месяц; при уходе студента с предоплатой возврат за непройденные месяцы
   оформляет бухгалтер вручную (возврат из аванса или корректировка);
   смена способа оплаты — только до первого урока; деньги при зачислении
   проводит только бухгалтер (менеджер фиксирует ожидаемую бронь).

1. **Отсутствие студента.** По умолчанию урок списывается, если группа его
   провела (как в учёте циклов тренеров). Альтернативы — в тарифе
   (`EXCEPT_EXCUSED`, `ATTENDED_ONLY`). Нужно утвердить правило.
2. **Удержание брони при отмене** — сумма и основание задаются бухгалтером
   вручную; формализованного правила (процент, сроки) нет.
3. **Лимиты**: скидка менеджера 10 %, лимит возврата бухгалтера не задан.
