# Бухгалтерия и расчёт зарплат (`apps.accounting`)

API: `/api/v1/accounting/` · интерфейс: `/accounting` (React) · валюта: KGS ·
периоды: 1–15 и 16–последний день месяца.

## Роли

| Роль | Что может |
|---|---|
| `accountant` (Бухгалтер) | Видит всю бухгалтерию; вносит платежи студентов и возвраты; ведёт зарплатные профили и правила, стоимость курсов и уроков в цикле; рассчитывает и пересчитывает начисления; добавляет корректировки; регистрирует и отменяет выплаты; выгружает отчёты. **Не утверждает** начисления (если не включено `ACCOUNTING_ACCOUNTANT_CAN_APPROVE`). |
| `director` (Директор) | Видит всё; утверждает начисления (по одному или все без ошибок), возвращает на исправление, переоткрывает утверждённые без выплат, решает по корректировкам утверждённых начислений, закрывает период; отчёты и журнал. |
| `admin` | Только просмотр бухгалтерии и журнала (управляет пользователями и ролями, не деньгами). В Django admin модели бухгалтерии — только для чтения. |
| любой сотрудник (Assistant, Team Lead, Trainer…) | «Моя зарплата» — только свои начисления и выплаты, только чтение (см. ниже). |

Бухгалтер и Директор, как Team Lead и Ассистент, никогда не получают
`is_staff`/`is_superuser` (`User.save()`), роль меняет только администратор.
Нельзя утверждать, корректировать или оплачивать **собственное** начисление.

## Изоляция бухгалтера

Бухгалтерия — отдельная зона доступа; бухгалтер не пользователь LMS.

* **Серверный барьер** — `apps.accounting.access.AccountingIsolationMiddleware`.
  Для ролей из `ACCOUNTING_ISOLATED_ROLES` (по умолчанию `("accountant",)`)
  открыты только `/api/v1/accounting/…` и `/api/v1/auth/login|refresh|me/`.
  Любой другой URL — API LMS (студенты, группы, программы, занятия,
  посещаемость, ДЗ, тренеры, аналитика, Assistant API), `/admin/`, схема API —
  отвечает `403` (`{"code": "accounting_only"}` для API). Пользователь
  определяется и по сессии, и по JWT, поэтому прямые URL, API-запросы и
  подставленные id закрыты одинаково, а новый эндпоинт LMS закрыт автоматически.
* **Django-группа `Accountant`** создаётся после `migrate` и содержит только
  разрешения `view/add/change` на финансовые модели (без `delete_*`, журнал
  аудита — только `view`). Права бухгалтера в API бухгалтерии проверяются через
  эти разрешения. При каждом сохранении пользователя-бухгалтера у него остаётся
  ровно эта группа, личные разрешения снимаются, `is_staff`/`is_superuser`
  сбрасываются — сам повысить себе права он не может (API пользователей и
  `/admin/` ему закрыты).
* **Минимум данных LMS.** Расчёт читает LMS через `services/activity.py` с
  ограниченным набором полей (id, группа, статус, даты). В API бухгалтерии
  активные студенты — только агрегатом (`students_count`, `student_days`);
  поиск студента для платежа отдаёт лишь id, ФИО и группу.
* **Фронтенд.** После входа бухгалтер сразу попадает на `/accounting`; любой
  маршрут LMS перенаправляет его туда же.

Чтобы так же изолировать директора: `ACCOUNTING_ISOLATED_ROLES = ("accountant", "director")`.

## «Моя зарплата» (Assistant, Team Lead, Trainer)

* Страница: `/my-salary` → `/assistant/my-salary` (Assistant) или
  `/app/my-salary` (Team Lead, Trainer); пункт «Моя зарплата» в меню роли.
* API: `GET /api/v1/accounting/my/salary/?year=&month=&period_type=` и
  `GET …/my/salary/report.pdf` (личный отчёт). Сотрудник — **всегда
  `request.user`**: параметров `employee`/`employee_id` нет, подставленные
  игнорируются. Только `GET` — `POST/PUT/PATCH/DELETE` отвечают 405; всё
  остальное в бухгалтерии этим ролям отвечает 403.
* Данные — из существующих моделей (`EmployeeSalaryProfile`, `SalaryRule`,
  `Payroll`, `PayrollLine`, `PayrollAdjustment`, `PayrollPayment`), отдельной
  таблицы нет: тип оплаты и действующая ставка (оклад или процент от курса),
  начисления текущего месяца по половинам 1–15 и 16–конец, история
  начислений с детализацией, история выплат, итоги и последняя выплата.
* Статусы: «Ожидает расчёта» (расчёта нет, черновик или возвращён на
  исправление — суммы не показываются), «Рассчитано, ожидает утверждения»,
  «Утверждено», «Частично выплачено», «Выплачено». Аннулированные скрыты.
* Карточки «Начислено / Выплачено / Остаток» — по утверждённым начислениям;
  ещё не утверждённая сумма показывается подсказкой отдельно.

## Модели

* `StudentPayment` — фактический платёж студента или возврат (`kind=refund`,
  обязательная ссылка `refund_of` на исходный платёж). Три даты: поступления
  (`received_date`) и период обучения (`service_start`–`service_end`). До этого
  модуля в проекте не было ни одной модели оплат, поэтому она добавлена здесь.
* `EmployeeSalaryProfile` — зарплатная карточка сотрудника (`users.User`).
* `SalaryRule` — версия правила: `FIXED`, `REVENUE_PERCENT`, `PER_STUDENT`,
  `PER_GROUP`, `BONUS`. Не редактируется: новая ставка = новая версия
  (`/salary-rules/{id}/new-version/`), старая закрывается днём раньше.
* `PayrollPeriod` — уникален по (год, месяц, половина), даты вычисляются сами.
* `Payroll` — один расчёт на (сотрудник, период) (уникальное ограничение).
* `PayrollLine` — строка расчёта со снимком ставки, процента, базы, количества
  и основания (`metadata`: платежи, студенты и их дни).
* `PayrollAdjustment` — премия / удержание / исправление.
* `PayrollPayment` — выплата (несколько на начисление, авансы).
* `PayrollAuditLog` — журнал, только добавление.
* `CoursePayrollSettings` — уроков в блоке (12/20), учитываемые предметы,
  правило учёта студентов; `CoursePriceVersion` — история тарифов.
* `CourseCycle` — блок группы; `CycleLesson` — его конкретные уроки;
  `CycleAccrual` — начисление тренеру за блок (снимок параметров, плановая
  дата выплаты, статус, в т.ч. «Требует проверки»).

Соответствие сущностям ТЗ: `SalaryPolicy` → `EmployeeSalaryProfile` +
`SalaryRule`; `CoursePricing` → `CoursePriceVersion`; `LessonBlock` →
`CourseCycle`; `LessonBlockItem` → `CycleLesson`; `PayrollEstimate` —
вычисляется на лету (`services/estimates.py`), не хранится; `PayrollAccrual`
→ `Payroll` + `PayrollLine` + `CycleAccrual`; `PayrollPayment`,
`PayrollAdjustment`, `PayrollAuditLog`, `PayrollPeriod` — как есть. Статусы
разделены: блок (`CourseCycle.status`), оценка (`ESTIMATED` /
`BLOCK_IN_PROGRESS` / `READY_FOR_ACCRUAL`), начисление (`CALCULATED` ≈
ожидает подтверждения, `APPROVED`, `REVIEW_REQUIRED` у начисления за блок),
оплата (`APPROVED` без выплат ≈ PENDING, `PARTIALLY_PAID`, `PAID`).

Финансовые записи не удаляются физически (`delete()` запрещён и на модели, и на
QuerySet) — только отмена (`VOID`) с причиной.

## Типы оплаты

Разрешены только два типа (профиль сотрудника и его правила — одного типа,
комбинированной схемы нет; бонусы и удержания — корректировками):

| Тип | Формула |
|---|---|
| `FIXED` — оклад | Полная сумма за **календарный месяц** одним расчётом в периоде «Весь месяц (оклад)» (`period_type=MONTH`, 1-е — последнее число); на половины 1–15 / 16–конец не делится. Не зависит от студентов, курсов, платежей и посещаемости. Неполный месяц — только по установленным условиям: правило или профиль начинают/прекращают действовать внутри месяца (приём, увольнение, новая ставка) → оклад × дни действия / дни месяца. Выплаты — отдельно, с датой и суммой; **аванс** — частичная выплата месячного начисления (`is_advance`), а не половина оклада. |
| `PERCENT` — процент от стоимости курса | За каждый **завершённый цикл** курса: `студенты × стоимость курса × процент / 100`. Фактические платежи, посещаемость и число уроков сверх цикла не влияют. |

Все суммы — `Decimal`, округление строки до 0.01 сома, половина вверх.
Значения первой версии модуля (`REVENUE_PERCENT`, `PER_STUDENT`, `PER_GROUP`,
`BONUS`, `COMBINED`) остаются только в истории: создать такие правила нельзя,
расчёт по профилю старого типа выдаёт ошибку «больше не поддерживается».

## Расчётные периоды по типу оплаты

* `FIXED` считается только в периоде «Весь месяц (оклад)»; массовый расчёт
  этого периода берёт только сотрудников на окладе. Попытка рассчитать оклад
  в половине месяца отклоняется (`wrong_period`), пустой расчёт не создаётся.
* `PERCENT` считается только в периодах 1–15 и 16–конец месяца.
* Сводка и отчёты за «Весь месяц» включают все расчёты месяца: оклады и обе
  половины процента.
* **Переход с прежней схемы** (оклад делился на половины): существующие
  данные и правила миграция `0004` не меняет (только списки вариантов). Если
  за месяц уже есть **утверждённый** полумесячный расчёт оклада, месячный
  расчёт засчитывает его отрицательной строкой «Зачёт оклада, начисленного по
  прежней схеме» — утверждённое не меняется, двойного начисления нет. Если
  есть **неутверждённый** полумесячный расчёт оклада — ошибка, блокирующая
  утверждение, пока бухгалтер его не аннулирует (сам расчёт ничего не меняет).

## Циклы по предметам

Циклы ведутся **отдельно для каждой пары «группа + предмет»** (`CourseCycle.subject`).
Программа на 144 урока (IT 48, English 48, Soft Skills 48) — это три независимых
счётчика: у каждого предмета свой номер цикла, проведённые и оставшиеся уроки,
прогресс и тренеры. Урок IT не меняет прогресс English и Soft Skills; сумма
уроков группы (например, 6 + 6 + 6) не завершает ни один блок; завершение
блока IT не завершает блоки остальных предметов.

* **Предмет урока** — `Lesson.subject`; **тренер урока** — `Lesson.teacher`, иначе
  тренер программы (`GroupTeacher`). Уроки без предмета — отдельный цикл
  «Без предмета». «Предметы с циклами» (`counted_subjects`) ограничивают учёт
  (например, только IT); пусто — все предметы курса и программ группы.
* **Тренеры цикла** — по фактическим урокам (`teacher_lessons`: тренер → уроков).
* **Начисление за блок предмета** — каждому тренеру, проводившему его уроки, при
  действующем правиле «Процент»:
  `студенты × тариф × процент тренера / 100 × (его уроки / уроков в цикле)`
  (`CycleAccrual.lessons_taught`, `share`). Один тренер провёл весь блок —
  полная сумма; замена 3 из 12 — 3/12 замене (по её ставке) и 9/12 основному.
  Смена тренера на проверку **не** отправляет. Тренер без правила «Процент» —
  его доля не начисляется и никому не передаётся (предупреждение в цикле).
  Сотрудник с правилом, привязанным к группе, который никогда не был в ней
  тренером, получает весь блок (основание — привязка, как и раньше).
* **Правило при нескольких тренерах** — настройка курса `trainer_split_rule`:
  `BY_LESSONS` (по умолчанию, пропорционально урокам) или `REVIEW` (доли
  предлагаются, решает бухгалтер — «Требует проверки»).
* **Второй блок предмета в том же месяце** — по-прежнему на проверку
  (`ACCOUNTING_REVIEW_REPEATED_MONTHLY_CYCLES`).
* **Без дублей**: один живой цикл с номером на группу и предмет, один открытый
  цикл на предмет, одно начисление на (цикл, сотрудник) — ограничения БД.
* **Переход с общего цикла группы** (миграции `0007`, `0008`): прежние циклы
  остаются историей (`per_subject=False`) со своими начислениями и выплатами;
  открытые общие циклы закрываются («Учёт переведён на циклы по предметам»).
  Уроки, уже учтённые общими циклами (по привязке, иначе все уроки до
  последнего урока последнего общего цикла), в предметные циклы не попадают —
  оплаченный урок не оплачивается дважды. Откат `0008` возможен, только пока
  ни один предметный цикл не завершён (иначе — понятная ошибка).
* API: `GET cycles/?status=&course=&group=&subject=&trainer=&search=` — у цикла
  `subject_name`, `lessons_done`, `lessons_remaining`, `progress_percent`,
  `subject_plan_lessons` (уроков предмета в плане курса), `trainer_lessons`,
  `accruals` с долями, `warnings`. Страница «Курсы и блоки» — строки по
  предметам внутри группы, свой прогресс-бар у каждого, фильтры и вкладки.

## Автоматический учёт уроков и начисление (`PERCENT`)

> Разделы ниже описывают механику порогов; с версии 0007 всё это действует
> **для каждого предмета группы отдельно** (см. «Циклы по предметам»).

* **Учёт уроков — автоматический**: уроки группы со статусом «Проведён» из
  LMS, с первого проведённого урока (необязательная дата «Учитывать уроки с»
  в настройках курса — только если нужно отсечь старую историю). Бухгалтер
  число уроков не вводит. Отменённые и запланированные уроки не считаются.
* **Интервал** — `required_lessons` в настройках курса (`CoursePayrollSettings`,
  раздел «Курсы и циклы»), не в коде: 12 → пороги 12, 24, 36, 48…;
  20 → 20, 40, 60… Там же — фиксированная стоимость курса за студента.
* **Порог достигнут — начисление создаётся сразу**: при сохранении урока
  (сигнал `post_save`/`post_delete` урока, после коммита) цикл фиксируется и
  тренеру создаётся `CycleAccrual` по его проценту:
  `студенты × стоимость курса × процент / 100`. Ничего не нужно запускать
  вручную; расчёт периода только включает готовые начисления строками.
  Подстраховка: синхронизация также идёт при расчёте, при открытии списка
  циклов и командой `python manage.py sync_course_cycles`.
* **Сохраняется** (цикл + начисление): группа и курс, номер цикла, уроков в
  цикле и порог (накопленные уроки), дата достижения порога, число студентов,
  стоимость курса, процент, сумма и **статус начисления**: «Начислено» →
  «Утверждено» (с утверждением расчёта; выплачено — по статусу расчёта),
  либо «Отменено» / «Сторнировано корректировкой» / «Требует ручной
  корректировки».
* **Период** — по дате достижения порога: 1–15 → первый, 16–конец → второй.
* **Студенты** — по правилу курса: по умолчанию активные в группе на дату
  порога; вариант — активные хотя бы один день цикла.
* **Кому** — сотруднику с правилом `PERCENT`, отвечавшему за группу на дату
  порога (история назначений тренеров); правило можно ограничить курсом или
  группой. Оклад (`FIXED`) — без интервальных начислений.
* **Без дублей**: один живой цикл с номером на группу и курс (уникальное
  ограничение) и одно начисление на (цикл, тренер). Повторное сохранение
  урока, повторный запуск и пересчёт ничего не дублируют.
* **Исправление урока после начисления** (урок отменили или удалили, порог
  больше не достигнут): цикл помечается «Отменён (уроки исправлены)» с
  причиной; неутверждённое начисление отменяется и убирается из черновика
  расчёта; утверждённое — не трогается, а сторнируется корректировкой
  «Исправление» на минус сумму, которая ждёт решения директора (отклонил —
  начисление остаётся в силе; переоткрыл расчёт — сторно не нужно). Если
  период уже закрыт — статус «Требует ручной корректировки». Всё — в журнале
  аудита. Когда порог снова достигнут, создаётся новый цикл и начисление.
* **Изменение интервала или цены** действует на новые циклы; завершённые
  циклы и утверждённые начисления сохраняют свой снимок.
* Порог, достигнутый задним числом в уже утверждённом периоде, начисляется в
  ближайшем рассчитываемом периоде с пометкой.

## Предварительная зарплата (оценка блока)

* Тренер видит оценку по каждому **незавершённому** блоку («Моя зарплата» →
  «Блоки в процессе», `GET my/estimates/`; бухгалтерия — `GET estimates/` и
  вкладка «Предварительные оценки» в «Курсы и блоки»):
  `ученики × текущий тариф курса × процент / 100`, прогресс `8 из 12`,
  «осталось провести», статус (`ESTIMATED` — уроков ещё нет,
  `BLOCK_IN_PROGRESS` — блок идёт, `READY_FOR_ACCRUAL` — порог достигнут,
  начисления ещё нет) и все использованные параметры.
* Оценка **считается на лету и нигде не хранится как деньги**: не начисление и
  не задолженность, не входит в «Начислено / Выплачено / Остаток», расчёты,
  аналитику и отчёты. Окончательное начисление создаётся при завершении блока
  по условиям **на дату завершения**, а не из оценки.
* Ожидаемая дата выплаты показывается, если её можно определить по
  календарю: дата урока, на котором будет достигнут порог, — из уже
  запланированных уроков группы; иначе «после завершения блока».
* Изменение состава группы, тарифа или процента сразу меняет оценку и не
  трогает утверждённые начисления.

## Плановые даты выплат (`services/payout.py`)

* Процент: блок завершён 1–15 → выплата **15-го** этого месяца; 16–конец →
  **1-го** следующего (31.12 → 01.01). Дата завершения — дата урока порога
  (не дата запуска синхронизации), часовой пояс `Asia/Bishkek`. Совпадает с
  периодом расчёта: 1–15 → 15-е, 16–конец → 1-е.
* Оклад: месячный календарь из настроек `ACCOUNTING_FIXED_PAYDAY_DAY` и
  `ACCOUNTING_FIXED_PAYDAY_NEXT_MONTH`; не настроен — дата не планируется
  (не выдумывается).
* Плановая дата — не факт перевода: `PAID` ставит только зарегистрированная
  выплата. Поле `planned_payment_date` есть у расчётов, начислений за блок,
  строк «Моей зарплаты»; просроченные видны в аналитике.

## История тарифов (`CoursePriceVersion`, раздел «Стоимость курсов»)

* Фиксированная цена обучения одного ученика за **месяц** (KGS), с датой
  начала, автором и **обязательной причиной**. Новая цена — новая версия
  (`POST pricing/`), предыдущая закрывается днём раньше; версии не
  редактируются и не удаляются (модель и QuerySet).
* Блок берёт цену на дату завершения и хранит снимок — новый тариф не меняет
  созданных начислений. Тариф задним числом на дату уже завершённого блока
  запрещён (`retroactive`): исправление — корректировкой.
* Первый тариф курса действует и на более раннюю историю (как раньше, когда
  цена была одна). `PATCH course-settings/` больше не меняет цену
  (`use_pricing`); при создании настроек цена становится первой версией.
* Это согласованная цена курса, а не поступившие платежи (`StudentPayment`).

## Блоки: уроки, предметы, спорные начисления

* **Уроки блока** (`CycleLesson`): при завершении блока фиксируются конкретные
  уроки (id, дата, фактический тренер). Частичный уникальный индекс
  `unique_live_cycle_lesson` не даёт одному уроку попасть в два действующих
  блока; у отменённого блока связи остаются историей (`is_live=False`).
* **Учитываемые предметы** (`CoursePayrollSettings.counted_subjects`): в блок
  входят только уроки этих предметов (например, только IT); пусто — все уроки
  группы, как раньше.
* **Требует проверки** (`CycleAccrual.status = REVIEW_REQUIRED`) — начисление
  создаётся, но в расчёт не входит и блокирует утверждение, пока бухгалтер не
  решит (`POST cycle-accruals/{id}/review/ {confirm, reason}`, основание
  обязательно, своё — нельзя):
  * **несколько тренеров** — только если в курсе выбрано правило `REVIEW`
    (по умолчанию доли по урокам начисляются автоматически);
  * **второй блок группы в том же календарном месяце** — месячная цена курса
    не начисляется дважды автоматически (настройка
    `ACCOUNTING_REVIEW_REPEATED_MONTHLY_CYCLES`, по умолчанию включена).
  Подтвердить — начисление войдёт в ближайший расчёт; отменить — история
  сохраняется, распределение между тренерами — корректировками.

## Направления и аналитика директора

* `EmployeeSalaryProfile.department`: IT, Soft Skills, Английский, Тимлиды,
  Ассистенты, Прочий персонал. Пусто — по роли (Team Lead, Ассистент, иначе
  «Прочий»). В расчёте хранится снимок (`Payroll.department`).
* `GET analytics/summary/?year&month[&department&employee&group&salary_type&status]`,
  `GET analytics/by-department/` — только чтение (бухгалтер, директор,
  администратор). Определения:
  * **начислено** — строки + применённые корректировки **утверждённых**
    расчётов месяца; неутверждённое — отдельно (`awaiting_approval_amount`);
  * **выплачено** — подтверждённые выплаты по этим расчётам; **остаток** —
    разница;
  * **переводы в месяце** (`cash_paid_in_month`) — выплаты с датой в месяце,
    за какой бы месяц ни было начисление;
  * сравнение с прошлым месяцем, история за 12 месяцев, ожидают утверждения,
    блоки на проверке, ближайшие и просроченные плановые выплаты;
  * предварительные оценки не входят никогда.
* `GET reports/teachers/` (+ `.xlsx`, `.pdf`) — отчёт по сотрудникам:
  строки начислений (группа, ученики, цена, процент, уроки/блок, сумма) и
  итог каждого расчёта. Выплаты относятся к расчёту целиком, поэтому
  «выплачено / остаток» — только в итоге расчёта (между группами не делятся),
  итоги по направлениям — по расчётам, без двойного счёта.

## Автоматизация (Celery в проекте нет)

* `python manage.py payroll_autorun [--calculate] [--date]` — раз в день
  (cron/планировщик хостинга): синхронизация блоков и начислений; с
  `--calculate` — периоды текущего месяца и расчёт неутверждённых (оклады — за
  месяц, процент — текущая половина); вывод ближайших и просроченных выплат.
  Повторный запуск ничего не дублирует — уникальность обеспечивают
  ограничения БД. Утверждение — только директор.
* `python manage.py payroll_reconcile [--json]` — сверка (только чтение):
  итоги расчётов против записей, статусы, переплаты, формулы начислений за
  блок, уроки в нескольких блоках, блоки без привязки уроков, перенесённые
  тарифы, профили без направления. Код выхода 1 при расхождениях.

## Исправление ошибочных правил (раздел «Зарплатные правила»)

У каждого последнего правила — кнопка **«Исправить»** или **«Заменить с даты»**
(какая — решает backend по полю `usage` правила).

* **Исправить** (`POST salary-rules/{id}/correct/`, причина обязательна) — пока
  правило не попало в утверждённые начисления (нет строк в утверждённых /
  выплаченных расчётах и нет утверждённых начислений за циклы). Меняются тип
  оплаты, ставка, курс/группа, метод, даты, комментарий; тип оплаты профиля
  меняется вместе с правилом (если это единственное правило сотрудника).
  Последствия: неутверждённые начисления за циклы пересчитываются или
  отменяются (остаются в истории), черновые расчёты пересчитываются, а
  неподходящие новому типу (оклад — месяц, процент — половины) аннулируются.
  Ничего не удаляется; в журнале — запись `correct` со старыми и новыми
  значениями.
* **Заменить с даты** (`POST salary-rules/{id}/replace/`) — если правило уже в
  утверждённых начислениях: старое закрывается днём раньше, создаётся новое
  (тип, ставка, основание). Дата — позже последнего утверждённого
  использования; смена типа — только с 1-го числа месяца. Смена типа
  запрещена, пока есть неутверждённые начисления процента за циклы до даты
  (процент → оклад) или неутверждённые расчёты оклада за прошлые месяцы
  (оклад → процент) — их сначала утверждают или аннулируют. Утверждённые
  расчёты, их строки и выплаты не меняются.
* Правила одного сотрудника, одного типа и одного основания не могут
  действовать одновременно — проверяется при создании, исправлении и замене
  (`overlap`).

## Прочие правила

* **Пересекающиеся правила** одного типа и основания — ошибка, блокирующая
  утверждение. Нет правил — ошибка «Не настроена ставка».
* **Платежи студентов** (`student-payments/`) — учёт поступлений и возвратов;
  на зарплату больше не влияют.
* **Предупреждения**: нет завершённых циклов в периоде, изменение начисления
  более чем на 50 % к предыдущему периоду.

## Жизненный цикл

`DRAFT → CALCULATED → APPROVED → PARTIALLY_PAID → PAID`, плюс `RETURNED`
(директор вернул на исправление; пересчёт возвращает в `CALCULATED`) и `VOID`
(аннулирован до утверждения).

* Пересчёт разрешён только в `DRAFT`/`CALCULATED`/`RETURNED`; повторный расчёт
  не создаёт дубликатов (строки заменяются, выплаты не трогаются).
* Утверждённое начисление не пересчитывается. Исправление — корректировкой
  (ждёт решения директора) или переоткрытием директором (только без выплат,
  с причиной; прежние строки и итоги сохранены в аудите записи `approve`).
* **Остаток** = начислено + применённые корректировки − подтверждённые выплаты.
* Выплата: сумма > 0, начисление утверждено, сумма ≤ остатка (если не включено
  `ACCOUNTING_ALLOW_OVERPAYMENT`), тот же номер документа не принимается дважды,
  заголовок `Idempotency-Key` (или поле `idempotency_key`) делает повторный
  запрос безопасным — возвращается та же выплата.
* Все операции — в `transaction.atomic()` с `select_for_update` начисления.
* Период закрывается директором, когда все начисления выплачены или
  аннулированы; после этого в нём ничего не меняется.

## Нерешённые бизнес-вопросы

1. **Месячная цена и несколько блоков в месяц.** Цена курса — за месяц, а
   начисление — за блок. Если у группы в одном месяце завершается второй блок,
   правило распределения месячной суммы не утверждено: такое начисление
   ставится на проверку бухгалтеру (подтвердить / отменить), а не начисляется
   молча. Нужно решение руководства (например, «один блок = один оплаченный
   месяц» или доля по урокам).
2. **Несколько тренеров в блоке предмета.** По умолчанию — пропорционально
   проведённым урокам, каждому по его ставке (правило курса `BY_LESSONS`).
   Нужно подтвердить: устраивает ли пропорция по урокам; что делать с долей
   тренера без правила «Процент» (сейчас не начисляется и не передаётся
   другим); нужен ли для некоторых курсов режим `REVIEW`.
8. **Месячная цена и предметы.** Тариф — за ученика в месяц на всю программу, а
   процент начисляется за блок каждого предмета (IT, English, Soft Skills —
   каждый от полной базы по своей ставке), как и до предметного учёта.
   Нужно подтвердить, что база для каждого предмета — полная цена, а не её
   доля по предмету.
9. **Размер блока по предметам.** Сейчас одинаковый для всех предметов курса
   (`required_lessons`); если у English и IT разные блоки — нужна настройка.
3. **Неполный месяц ученика.** Ученик учитывается по правилу курса (активен
   на дату завершения блока или хотя бы один день блока); пропорционального
   учёта нет и без утверждённого правила не вводится.
4. **Оклад при приёме/увольнении в середине месяца** — по дням действия
   профиля/правила (действующее правило модуля); иная пропорция требует
   решения.
5. **Календарь выплаты оклада** — не задан (настройка), дата не планируется.
6. **Направления тренеров** — в LMS их нет; бухгалтер указывает в профиле.
7. **Предметы блока** — по умолчанию считаются все уроки группы; для групп с
   несколькими предметами нужно указать учитываемые предметы курса.

## Очистка данных бухгалтерии (Django Admin, только суперпользователь)

Django Admin → «Бухгалтерия и зарплаты» → «Обслуживание базы данных: очистка
данных» (`/admin/accounting/payrollauditlog/maintenance/purge/`). Пункт меню
виден только с правом `accounting.purge_accounting_data` (есть только у
суперпользователя); само представление проверяет `is_superuser` и отвечает
403 всем остальным. Бухгалтеру `/admin/` закрыт middleware изоляции.

| Режим | Удаляет (в этом порядке) | Сохраняет |
|---|---|---|
| A — расчёты зарплаты | `cycleaccrual`, `payrollauditlog`, `payrollpayment`, `payrolladjustment`, `payrollline`, `payroll`, `payrollperiod` | правила, профили, циклы и их уроки, настройки курсов, тарифы, платежи студентов |
| B — полная очистка | всё из A + `cyclelesson` (зависимая: PROTECT на цикл), `coursecycle`, `salaryrule`, `employeesalaryprofile`, `coursepayrollsettings` (+ связь «учитываемые предметы»), `studentpayment` с возвратами; `coursepriceversion` — только по отдельному флажку | историю тарифов (если флажок не отмечен) |

Пользователи, тренеры, группы, курсы, предметы, уроки и посещаемость не
удаляются никогда.

Защита: на странице — количество записей по каждой таблице и предупреждение
о необратимости; нужно ввести `DELETE ACCOUNTING` и подтвердить резервную
копию, для режима B — ещё `FULL RESET`. Если количества изменились после
открытия страницы, удаление не выполняется. Удаление — `services/maintenance.py`:
одна `transaction.atomic()`, обычный `QuerySet.delete()` (внешние ключи,
`on_delete` и сигналы работают; неверный порядок → `ProtectedError` → откат),
самоссылки PROTECT (версии правил и тарифов, возвраты) — от листьев к корню,
без сырого SQL и без отключения проверок. Запрет удаления финансовых записей
снимается только внутри этой операции (`models.maintenance_delete`). После
удаления проверяется, что удаляемые таблицы пусты, а сохраняемые не
изменились, — иначе откат. В журнал аудита пишется одна запись об операции
(`purge_payroll` / `purge_full`: кто, когда, сколько удалено).
