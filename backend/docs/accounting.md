# Бухгалтерия и расчёт зарплат (`apps.accounting`)

API: `/api/v1/accounting/` · интерфейс: `/accounting` (React) · валюта: KGS ·
периоды: 1–15 и 16–последний день месяца.

## Роли

| Роль | Что может |
|---|---|
| `accountant` (Бухгалтер) | Видит всю бухгалтерию; вносит платежи студентов и возвраты; ведёт зарплатные профили и правила; рассчитывает и пересчитывает начисления; добавляет корректировки; регистрирует и отменяет выплаты; выгружает отчёты. **Не утверждает** начисления (если не включено `ACCOUNTING_ACCOUNTANT_CAN_APPROVE`). |
| `director` (Директор) | Видит всё; утверждает начисления (по одному или все без ошибок), возвращает на исправление, переоткрывает утверждённые без выплат, решает по корректировкам утверждённых начислений, закрывает период; отчёты и журнал. |
| `admin` | Только просмотр бухгалтерии и журнала (управляет пользователями и ролями, не деньгами). В Django admin модели бухгалтерии — только для чтения. |
| любой сотрудник | `/accounting/my/payrolls/` — только свои **утверждённые** начисления, выплаты и PDF расчётного листа. |

Бухгалтер и Директор, как Team Lead и Ассистент, никогда не получают
`is_staff`/`is_superuser` (`User.save()`), роль меняет только администратор.
Нельзя утверждать, корректировать или оплачивать **собственное** начисление.

## Модели

* `StudentPayment` — фактический платёж студента или возврат (`kind=refund`,
  обязательная ссылка `refund_of` на исходный платёж). Три даты: поступления
  (`received_date`) и период обучения (`service_start`–`service_end`). До этого
  модуля в проекте не было ни одной модели оплат, поэтому она добавлена здесь.
* `EmployeeSalaryProfile` — зарплатная карточка сотрудника (`users.User`).
* `SalaryRule` — версия правила: `FIXED`, `REVENUE_PERCENT`, `PER_STUDENT`,
  `PER_GROUP`, `BONUS`. Не редактируется: новая ставка = новая версия
  (`/salary-rules/{id}/new-version/`), старая закрывается днём раньше.
* `PayrollPeriod` — уникален по (год, месяц, половина), даты вычисляются сами.
* `Payroll` — один расчёт на (сотрудник, период) (уникальное ограничение).
* `PayrollLine` — строка расчёта со снимком ставки, процента, базы, количества
  и основания (`metadata`: платежи, студенты и их дни).
* `PayrollAdjustment` — премия / удержание / исправление.
* `PayrollPayment` — выплата (несколько на начисление, авансы).
* `PayrollAuditLog` — журнал, только добавление.

Финансовые записи не удаляются физически (`delete()` запрещён и на модели, и на
QuerySet) — только отмена (`VOID`) с причиной.

## Формулы

Все суммы — `Decimal`, округление каждой строки до 0.01 сома, половина вверх
(`ACCOUNTING_ROUNDING_QUANTUM`).

| Правило | Метод | Формула за период |
|---|---|---|
| Оклад | `SPLIT` (по умолчанию) | оклад × доля половины (по умолчанию 50/50, настраивается `first_half_share`) × дни действия / дни периода |
| Оклад | `PRORATE_DAYS` | оклад × дни действия в периоде / дни месяца |
| За группу | `PRORATE_DAYS` (по умолчанию) | ставка × дни, когда группа существовала **и** сотрудник за неё отвечал / дни месяца |
| За группу | `SPLIT` | ставка × доля половины × эти дни / дни периода |
| За студента | `STUDENT_DAYS` (по умолчанию) | ставка × Σ(дни активности студента в периоде) / дни месяца |
| За студента | `SNAPSHOT` | ставка × студенты, активные на конец периода × дни действия / дни месяца |
| Процент | — | Σ учитываемых платежей группы × процент / 100 (строка на каждую группу) |
| Бонус | — | разово, в периоде, куда попадает дата начала правила |

Пример ТЗ: сентябрь (30 дней), A активен весь месяц, B — с 16-го:
первая половина 11 000 × 15/30 = 5 500, вторая 11 000 × 30/30 = 11 000,
месяц = 16 500 сом.

## Принятые бизнес-правила (настраиваемые места)

* **Активный студент** (`services/activity.py`) — по истории
  `StudentStatusEvent`, а не текущему состоянию: активен в день D, если на D
  статус «Активен» и он в группе. Пауза, завершение и деактивация — не активен;
  день ухода не считается, день возврата — считается. Перевод меняет группу с
  даты перевода. Первый день — `enrollment_date`.
* **Уникальный студент**: один студенто-день учитывается для сотрудника один
  раз, даже если студент попадает под несколько групп или правил
  (повтор — предупреждение).
* **Ответственный за группу** — по `TrainerAssignment` (история тренеров).
  Если правило привязано к конкретной группе, а сотрудник в ней никогда не был
  тренером (куратор, программист), основанием служит сама привязка.
* **База процента** (`revenue_basis`):
  * `RECEIVED` (по умолчанию) — подтверждённые платежи с датой поступления в
    периоде; платёж закрепляется за тренером, отвечавшим за группу в день
    поступления (предоплата до первого назначения — за первым тренером).
    Платёж за несколько месяцев учитывается один раз.
  * `ALLOCATED` — платёж распределяется поровну по дням периода обучения
    (накопительное округление: доли всех периодов в сумме дают ровно платёж) и
    учитывается за дни, когда сотрудник отвечал за группу.
* **Возвраты** (`refund_policy`): `DEDUCT` — отдельной строкой «Корректировка
  возврата» в периоде возврата, только если исходный платёж относился к этому
  сотруднику; в строке — ссылка на исходный платёж и начисление, куда он вошёл.
  Утверждённые начисления не меняются. `IGNORE` — возвраты не влияют на зарплату.
* **Один платёж — одно начисление**: если два правила сотрудника покрывают одну
  группу, платёж учитывается один раз (предупреждение).
* **Пересекающиеся правила** одного типа и основания — ошибка расчёта,
  блокирующая утверждение. Нет правил — ошибка «Не настроена ставка».
* **Предупреждения** массового расчёта: нет студентов / нет платежей / повторы /
  изменение более чем на 50 % к предыдущему периоду.

## Жизненный цикл

`DRAFT → CALCULATED → APPROVED → PARTIALLY_PAID → PAID`, плюс `RETURNED`
(директор вернул на исправление; пересчёт возвращает в `CALCULATED`) и `VOID`
(аннулирован до утверждения).

* Пересчёт разрешён только в `DRAFT`/`CALCULATED`/`RETURNED`; повторный расчёт
  не создаёт дубликатов (строки заменяются, выплаты не трогаются).
* Утверждённое начисление не пересчитывается. Исправление — корректировкой
  (ждёт решения директора) или переоткрытием директором (только без выплат,
  с причиной; прежние строки и итоги сохранены в аудите записи `approve`).
* **Остаток** = начислено + применённые корректировки − подтверждённые выплаты.
* Выплата: сумма > 0, начисление утверждено, сумма ≤ остатка (если не включено
  `ACCOUNTING_ALLOW_OVERPAYMENT`), тот же номер документа не принимается дважды,
  заголовок `Idempotency-Key` (или поле `idempotency_key`) делает повторный
  запрос безопасным — возвращается та же выплата.
* Все операции — в `transaction.atomic()` с `select_for_update` начисления.
* Период закрывается директором, когда все начисления выплачены или
  аннулированы; после этого в нём ничего не меняется.

## API

| Метод | Endpoint |
|---|---|
| GET | `dashboard/?year=&month=[&period_type=]` или `?period=` |
| GET | `employees/` (фильтры: `search`, `salary_type`, `program`, `group`, `payment_status`) |
| GET/POST | `salary-profiles/`, `salary-rules/`; POST `salary-rules/{id}/new-version/`, `salary-rules/{id}/deactivate/` |
| GET/POST | `student-payments/`; POST `student-payments/{id}/void/` |
| GET/POST | `periods/` (POST идемпотентен); POST `periods/{id}/calculate/`, `periods/{id}/approve/`, `periods/{id}/close/` |
| GET | `payrolls/`, `payrolls/{id}/` |
| POST | `payrolls/calculate/`, `payrolls/{id}/recalculate/`, `approve/`, `return/`, `reopen/`, `void/` |
| GET/POST | `payrolls/{id}/payments/`, `payrolls/{id}/adjustments/` |
| POST | `payments/{id}/void/`, `adjustments/{id}/decide/`, `adjustments/{id}/void/` |
| GET | `payrolls/{id}/report.pdf/`, `payrolls/{id}/report.xlsx/` |
| GET | `reports/payroll.pdf`, `reports/payroll.xlsx` (`year`+`month` — полный месяц, + `period_type` — половина) |
| GET | `audit-log/`, `my/payrolls/`, `my/payrolls/{id}/report.pdf/` |

Схема — в OpenAPI (`/swagger-ui/`, тег *Accounting*).

## Настройки

```
ACCOUNTING_ACCOUNTANT_CAN_APPROVE=False   # бухгалтер утверждает сам
ACCOUNTING_ALLOW_OVERPAYMENT=False        # выплата сверх остатка
ACCOUNTING_ROUNDING_QUANTUM=0.01          # шаг округления
```

## Перед запуском в production

* Сделать резервную копию БД перед `migrate` (миграции только добавляют
  таблицы и роли, данные не удаляются).
* Согласовать с руководством значения по умолчанию из раздела «Принятые
  бизнес-правила» — каждое переключается в правиле сотрудника.
* Внести платежи студентов за текущий период (до модуля их в системе не было).
