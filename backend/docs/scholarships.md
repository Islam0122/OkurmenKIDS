# Стипендиальная система (apps.scholarships)

Ежемесячная стипендия за **предыдущий завершённый период** с оценкой студента
по **всем** предметам, которые он проходил в этом периоде.

## 1. Что переиспользуется из LMS

| Данные | Источник |
|---|---|
| Студент, статус, группа | `academy.Student` (+ новое поле `enrollment_date`) |
| История пауз/ухода/возврата | `academy.StudentStatusEvent` |
| Занятия, предмет, отмена, «ДЗ не требуется» | `academy.Lesson` |
| Посещаемость | `academy.Attendance` (уникальна на студента+занятие) |
| Домашние задания | `academy.Homework` + `academy.HomeworkResult` |
| Тренер занятия | `Lesson.effective_teacher` / `Lesson.objects.for_teacher` |
| Роли и доступ | `users.User.Role` (ADMIN / TEACHER) |

Новое: оценка тренера по студенту (`TrainerFeedback`) — раньше такой модели не
было (`apps.feedback` — это опросы родителей/студентов, другое).

Изменение существующей модели: `Student.enrollment_date` (миграция
`academy/0017`). Существующим студентам проставляется самая ранняя
подтверждаемая данными дата: дата создания записи или первое занятие с
отметкой посещаемости, если оно раньше. Новые студенты по умолчанию получают
сегодняшнюю дату; дату можно исправить в админке и через API.

## 2. Бизнес-правила

### Период оценки (календарный месяц)
Цикл, начисляемый в день D месяца, оценивает месяц, закончившийся накануне:

| Дата начисления | Цикл | Оцениваемый период |
|---|---|---|
| 01.10 | 1-е | 01.09 – 30.09 (прошлый календарный месяц) |
| 15.10 | 15-е | 15.09 – 14.10 |

Выбран календарный месяц, а не «годовщина зачисления»: весь отчётный контур
LMS (отчёты тренеров, отчёт академии) помесячный, а рейтинг «топ-20» требует
общего для всех периода. Период всегда заканчивается **до** даты начисления,
поэтому текущий незавершённый месяц не может быть оценён; сформировать
период с датой начисления в будущем нельзя.

### Стипендиальный период — главный объект
Всё остальное (оценки студентов, стипендиаты, оценки тренеров, журнал)
принадлежит периоду и открывается внутри него. Два вида периодов, одна
модель `ScholarshipPeriod`:

* **ежемесячный цикл** (`award_day` = 1 или 15) — формируется по
  расписанию, даты вычисляются автоматически (см. ниже) и не меняются;
* **ручной период** (`award_day` пустой) — администратор задаёт название
  (по умолчанию «Стипендия»), дату начала, дату окончания и лимит.
  `evaluation_date` = день после окончания. Если период уже закончился,
  рейтинг рассчитывается сразу; если ещё идёт — период пустой (тренеры
  уже могут вносить оценки), расчёт — кнопкой «Рассчитать» после окончания
  или ежедневной командой `run_scholarship_schedule`. Рассчитать или
  утвердить незавершённый/нерассчитанный период нельзя. Одинаковые даты
  у двух ручных периодов запрещены.

### Лимит стипендиатов
`ScholarshipPeriod.max_recipients` — лимит конкретного периода (при
создании по умолчанию берётся из настроек); `null` = **без ограничения**
(стипендию получают все допущенные). Правила (`services/generation.py`):

* при расчёте стипендию получают первые N допущенных по рейтингу;
* вручную можно **назначить** стипендию допущенному студенту и **убрать**
  её (только черновик) — 21-го при лимите 20 назначить нельзя:
  «Лимит стипендиатов достигнут: 20 из 20.» Сначала увеличьте лимит или
  уберите одного студента;
* лимит нельзя сделать меньше текущего числа стипендиатов; увеличение
  лимита само никого не добавляет (назначьте вручную или пересчитайте);
* «Пересчитать» заново составляет список по рейтингу — ручные изменения
  сбрасываются (интерфейс предупреждает);
* даты ручного периода меняются только до расчёта; после утверждения
  меняется только название.

Все изменения периода и списка стипендиатов пишутся в журнал периода.

### Право на стипендию (первая стипендия)
Студент участвует в распределении, только если учился **весь** период:
`enrollment_date <= начало периода`. Пример: зачисление 1 сентября → первая
стипендия 1 октября за сентябрь. Зачисление 10 сентября → сентябрь неполный,
первая стипендия 1 ноября за октябрь.

Статусы допуска (`EligibilityStatus`), проверяются по порядку:

1. `incomplete_data` — не указана дата начала обучения;
2. `not_full_period` — зачислен после начала периода или повторно
   активирован/вернулся с паузы внутри периода;
3. `inactive` — текущий статус не «Активен», либо в периоде была
   деактивация/пауза/завершение обучения;
4. `no_data` — нет учитываемых занятий (или меньше `min_marked_lessons`);
5. `incomplete_data` — нет оценки тренера хотя бы по одному учитываемому
   предмету (если `require_complete_feedback`);
6. `below_threshold` — итоговый балл ниже `min_overall_score`;
7. иначе `eligible`.

Баллы считаются и сохраняются и для недопущенных — для прозрачности.

### Режим начисления (1-е и 15-е число)
Настраивается в `ScholarshipConfiguration.award_mode`:

* **monthly** (по умолчанию) — единственный цикл 1-го числа. Запуск
  15-го ничего нового не начисляет (цикл 1-го уже существует → пропуск).
* **twice_monthly** — два **независимых** цикла: 1-го (01–конец прошлого
  месяца) и 15-го (15-е прошлого – 14-е текущего). У каждого свой лимит
  получателей; один студент может получить стипендию в обоих циклах, но не
  дважды в одном.

Второй режим — лишь техническая возможность; решение, нужен ли он, за
академией (см. «Открытые вопросы»).

### Формула
Для каждого предмета студента:

* **Посещаемость** = (присутствовал + опоздал) / (присутствовал + опоздал +
  отсутствовал) × 100. «Уважительная причина» исключается из знаменателя.
  Отменённые занятия не учитываются.
* **ДЗ** = зачтено / задано × 100. Задано = все `Homework` на занятиях
  студента в периоде, кроме занятий «ДЗ не требуется» и занятий, пропущенных
  по уважительной причине. «Сдано»/«Проверено» = 1, «С опозданием» =
  `late_homework_credit` (по умолчанию 0,5), «Не сдано» или нет результата = 0.
  Нет заданий по предмету → компонента нет, веса предмета перенормируются.
* **Оценка тренера** = среднее четырёх критериев (1–5: прогресс,
  активность, дисциплина, понимание) ÷ 5 × 100; несколько тренеров по
  предмету — среднее их оценок. **Отсутствие оценки = 0**, никогда не 100.
* **Балл предмета** = 0,40·посещаемость + 0,30·ДЗ + 0,30·оценка тренера
  (веса настраиваются, сумма обязана быть 1,00).

**Итоговый балл** = среднее баллов предметов. По умолчанию все предметы
равны (`equal`) — у студента с одним предметом нет преимущества перед
студентом с тремя, и наоборот. Альтернатива `lesson_weighted` — вес
предмета = число учитываемых занятий. Итоговые «посещаемость / ДЗ / оценка
тренера» студента агрегируются так же. Округление — один раз, до 0,01,
ROUND_HALF_UP; все расчёты в `Decimal`.

### Какие занятия и предметы учитываются
* Занятия периода (кроме отменённых), по которым у студента есть отметка
  посещаемости. Одно занятие не может учесться дважды (уникальность
  `Attendance`).
* Смена группы в периоде: учитываются отмеченные занятия и старой, и новой
  группы.
* Проведённое занятие текущей группы без отметки посещаемости не считается
  пропуском — это «без отметки» и предупреждение о данных.
* Предмет, по которому нет учитываемых занятий (только уважительные или
  только неотмеченные), показывается в разбивке, но не входит в итог
  (вес 0), с предупреждением. Ни один предмет не пропадает молча.
* Занятия без указанного предмета попадают в строку «Без предмета»
  (без компоненты оценки тренера).

### Рейтинг и лимит
Допущенные студенты сортируются детерминированно:
итоговый балл ↓ → посещаемость ↓ → ДЗ ↓ → оценка тренера ↓ → более ранняя
дата начала обучения → меньший id студента. Случайного выбора нет. Первые
`max_recipients` (по умолчанию 20) получают стипендию со статусом «Ожидает
утверждения». При делении места на границе лимита решает цепочка
тай-брейков, а не случай.

### Защита от дубликатов
* `ScholarshipPeriod`: уникален `(award_day, period_start)` — цикл
  существует один раз, кто бы и сколько раз его ни запускал
  (`get_or_create` в транзакции).
* `ScholarshipAward`: уникальны `(student, period)` и `(period, rank)`;
  `ScholarshipEvaluation`: `(period, student)` и `(period, rank)`.
* Пересчёт и утверждение блокируют строку периода (`select_for_update`) и
  перепроверяют статус; утверждённый период нельзя пересчитать или
  утвердить повторно. Проверено тестами на PostgreSQL с параллельными
  потоками.

### Жизненный цикл периода
1. Формирование (автоматически или вручную) → статус «Черновик»; все
   параметры конфигурации копируются в период (снимок).
2. Тренеры вносят оценки за период; администратор проверяет/исправляет.
3. «Пересчитать» — пересобирает оценки и рейтинг (сколько угодно раз).
4. «Утвердить» — стипендии получают статус «Утверждена»; после этого
   пересчёт и изменение оценок тренеров закрыты.

Если включено `auto_approve`, шаг 4 выполняется сразу при формировании
(не рекомендуется при `require_complete_feedback`: оценки тренеров ещё не
внесены).

## 3. Настройка

Админка → «Стипендии» → «Настройки». Миграция создаёт активную
конфигурацию по умолчанию: 20 получателей, веса 0,40/0,30/0,30, раз в месяц,
все предметы равны, ДЗ с опозданием = 0,5, обязательная оценка тренера,
ручное утверждение. Активной может быть только одна конфигурация.

## 4. Автоматизация

Celery в проекте нет, поэтому используется идемпотентная команда:

```bash
python manage.py run_scholarship_schedule            # сегодня (Asia/Bishkek)
python manage.py run_scholarship_schedule --date 2026-10-01
```

Её нужно запускать **раз в день** (Railway Cron / crontab), например
`10 0 * * *` по Бишкеку. Команда формирует последний наступивший цикл для
каждого настроенного дня; уже сформированные пропускаются, поэтому
пропущенный запуск догоняется на следующий день. Каждый запуск (успех,
пропуск, ошибка) пишется в «Журнал запусков» и в logger `apps.scholarships`.
Дата «сегодня» берётся через `timezone.localdate()` (TIME_ZONE проекта).

Та же команда рассчитывает ручные периоды, которые закончились, но ещё не
рассчитаны.

Вручную: админка → «Стипендиальные периоды» → «Создать период» → ссылка
«Сформировать цикл вручную», или
`POST /api/v1/scholarship-periods/generate/`.

| Метод | URL | Кто | Назначение |
|---|---|---|---|
| GET | `scholarship-periods/` | Админ; тренер (только даты/статус) | Список периодов |
| GET | `scholarship-periods/{id}/` | Админ; тренер (даты/статус) | Период |
| POST | `scholarship-periods/` | Админ | Создать ручной период `{title?, period_start, period_end, max_recipients: int\|null}` |

| POST | `scholarship-periods/{id}/awards/` | Админ | `{evaluation}` — назначить стипендию (400 при достигнутом лимите) |

| POST | `scholarship-periods/{id}/recalculate/` | Админ | Пересчёт (только черновик) |

| GET | `scholarship-evaluations/?period=&student=&eligibility_status=` | Админ | Оценки студентов |
| GET | `scholarship-evaluations/{id}/` | Админ | С разбивкой по предметам и предупреждениями |

Правила доступа: рейтинг, оценки студентов, стипендии, аналитика —
только администратор (403 тренеру). Тренер видит и пишет только свои
оценки и только по студентам и предметам, которые он реально вёл в этом
периоде; после утверждения периода изменения закрыты. Формирование и
утверждение: суперпользователь, роль ADMIN или явные права
`scholarships.generate_scholarshipperiod` / `approve_scholarshipperiod`.

## 6. Интерфейс

* **Django Admin → «Стипендии»** — в меню четыре пункта:
  * **Стипендиальные периоды** — карточки периодов: название, даты, статус
    (🟡 В процессе / 🟢 Завершён), «Студенты N / лимит», средний балл,
    сумма, кнопка «Открыть»; остальные действия — в меню ⋮. Кнопка
    «Создать период» (название, даты, лимит 10 / 20 / 30 / своё число /
    без ограничения, проверка дат и лимита прямо в форме).
  * Внутри периода — **дашборд**: всего студентов, стипендиатов N / лимит,
    средний балл, общая сумма; вкладки «Студенты» (№, студент, группа,
    балл, 🏆, статус, «Назначить» / «Убрать»), «Предметы», «Отчёт»,
    «Журнал»; ссылка на оценки тренеров периода. Карточка оценки
    студента (разбивка по предметам, история) открывается по имени.
  * **Отчёты** — сводка по всем периодам и подробный отчёт выбранного:
    всего студентов, участвуют, не допущены, лимит, выбрано, получили,
    не получили, средний балл, сумма; стипендии по месяцам.
  * **Стипендии** — все назначенные стипендии; **Настройки** — параметры
    расчёта по умолчанию.

  Разделы «Оценки студентов», «Оценки тренеров», «Журнал запусков»
  остались в админке, но открываются из периода, а не из меню.
* **Портал (frontend) → «Стипендии»**: тренер — список студентов для оценки и
  форма оценки (1–5 по четырём критериям, без предзаполнения); администратор —
  метрики, рейтинг, пересчёт и утверждение.
* Студенческого интерфейса нет: в LMS нет учётных записей студентов.

## 7. Ограничения и открытые вопросы для академии

1. **Режим 15-го числа.** По умолчанию 15-е ничего не начисляет. Если
   академии нужны две независимые выплаты — включить `twice_monthly`;
   если 15-е должно означать что-то другое (например, срок утверждения),
   это нужно уточнить.
2. **Сумма стипендии** — поле необязательное; в проекте нет платёжного
   модуля, выплаты не создаются.
3. **Выпускники.** Студент, завершивший обучение до даты начисления,
   получает статус `inactive` за последний месяц. Если он должен получить
   стипендию за последний полный месяц — нужно решение академии.
4. **Отзыв утверждённой стипендии** не реализован; освободившееся место
   автоматически не переходит следующему.
5. **Статус студента** проверяется на момент расчёта: пересчёт черновика
   после смены статуса может изменить допуск.
6. **Дата начала обучения** у существующих студентов проставлена
   автоматически (см. §1) — стоит проверить её до первого утверждения.
7. **История переводов между группами** в LMS не хранится; поэтому
   «без отметки» считается только по текущей группе студента.
8. **Оценки тренеров привязаны к периоду.** Их можно вносить только после
   формирования периода (1-го числа). Поэтому `auto_approve` вместе с
   `require_complete_feedback` даёт 0 стипендий (все «неполные данные»), а
   удаление и повторное формирование черновика теряет уже внесённые оценки.
9. **Один пропущенный отзыв блокирует студента.** На демо-данных при
   `require_complete_feedback` каждый месяц ~9–10% студентов получают
   «неполные данные». Возможно, нужен срок сдачи оценок для тренеров.
10. **Предмет без ДЗ** (например, Soft Skills) считается только по
    посещаемости и оценке тренера и легко даёт высокий балл, что при равном
    весе предметов поднимает итог студентам с таким предметом.
11. **Полные совпадения на границе лимита** (например, два 100.00) решаются
    по дате зачисления, затем по id. Детерминированно, но спорно —
    возможно, нужен общий ранг или ручное решение администратора.

## 9. Демо-данные для проверки

```bash
python manage.py seed_scholarship_demo                  # 400 студентов, seed 42, опорная дата = сегодня
python manage.py seed_scholarship_demo --students 1000  # любой объём (минимум 20)
python manage.py seed_scholarship_demo --today 2026-09-26 --seed 42   # полностью воспроизводимо
python manage.py seed_scholarship_demo --reset          # удалить демо и создать заново
python manage.py seed_scholarship_demo --clear          # удалить ТОЛЬКО демо-данные
python manage.py seed_scholarship_demo --no-checks      # без автоматических проверок
```

Только для dev/test баз: при `DJANGO_ENV=production` команда отказывается
работать (и генерация, и `--clear`). Код — `apps/scholarships/demo/`, в
миграциях и моделях демо-данных нет.

**Что создаётся** (реальные модели LMS, ничего нового): 4 программы
(`Course`), 5 предметов, ~1 группа на 16 студентов (у групп 1–5 предметов,
поэтому у студентов 1–5 предметов), тренеры (у части групп — два тренера по
одному предмету), расписание, занятия 2–3 раза в неделю за 4 полных месяца
+ текущий месяц до вчерашнего дня (~3% отменены), посещаемость, ДЗ и
результаты, оценки тренеров, 4 стипендиальных периода (3 утверждены,
последний — черновик). Профили успеваемости (top/strong/average/weak/very
weak) используются только при генерации. Пограничные случаи: поздние и
недавние зачисления, пауза и уход, неотмеченные занятия, ДЗ без результата,
отсутствующие/неполные оценки тренеров, а также сценарии A–H и T1–T4
(ничья) — их id печатаются в сводке.

**Метки демо-данных** (`apps/scholarships/demo/namespace.py`), `--clear`
удаляет только строки с ними:

| Данные | Метка |
|---|---|
| Группы, программы | имя начинается с `SCH-DEMO-` |
| Студенты | телефон начинается с `+000-SCHDEMO-` (невалидный код страны) |
| Тренеры и демо-админ | логин `schdemo_*` **и** e-mail `@scholarship-demo.invalid` |
| Стипендиальные периоды | `generated_by` = демо-админ |

Предметы — общий справочник: переиспользуются и не удаляются. Периоды
оценивают **всех** студентов базы, поэтому если в базе есть не-демо
студенты, периоды не создаются (данные LMS создаются, причина печатается).
`--clear` отказывается удалять демо-период с утверждёнными стипендиями
не-демо студентов.

После генерации команда запускает 15 проверок: 1/2/3+ предмета, только
завершённый месяц, первый месяц, лимит 20, рейтинг, тай-брейк,
отсутствующие оценки и ДЗ, посещаемость (независимый пересчёт), защита от
дубликатов, 1-е и 15-е число, производительность (время и число SQL).
Проверки, которым нужно что-то записать, выполняются в транзакции с
откатом.
