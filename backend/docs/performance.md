# Общая статистика (apps.performance)

Отдельный сайт «OkurmenKIDS — Общая статистика» — **не страница кабинета
LMS** (нет в меню, свой layout): посещаемость, выполнение домашних заданий,
активные группы и активные студенты — по каждому дню месяца. Рассчитан и на
постоянный показ на телевизоре в офисе.

* Сайт: `/monthly-performance` (например,
  `https://okurmen-kids-drab.vercel.app/monthly-performance`), режим
  телевизора — `?tv=1`. На своём домене — сборка фронтенда с
  `VITE_APP_MODE=statistics` (см. frontend/README.md).
* API: `/api/v1/monthly-performance/`.

## Доступ

Сайт открыт только своим — двумя способами:

1. **Вход сотрудника** — те же логин и пароль, что в LMS (любая должность;
   если сотрудник уже вошёл в LMS в этом браузере — сразу без входа).
2. **Ключ «только чтение»** (`DashboardAccessKey`) — для телевизора, где
   никто не входит в LMS. Ключ открывает **только** GET
   `/api/v1/monthly-performance/*` (заголовок `X-Dashboard-Key`): ни один
   другой эндпоинт LMS его не принимает, корректировать цифры по ключу нельзя.
   В базе хранится только SHA-256 ключа.

Создать ключ (показывается один раз):

```bash
python manage.py create_dashboard_key "Телевизор в офисе" [--days 365]
```

или Django admin → «Общая статистика: ключи доступа» → «Добавить». Открыть на
телевизоре: `<сайт>/monthly-performance?key=<ключ>&tv=1` — ключ запоминается в
браузере и сразу убирается из адресной строки. Отключить — снять «Активен»
(или задать «Действует до»).

API отдаёт только итоговые цифры академии — ни имён, ни групп, ни контактов.
На отдельном домене добавьте его в `STATISTICS_SITE_ORIGINS` (CORS; заголовок
`X-Dashboard-Key` уже разрешён).

## Показатели одного дня (`services/metrics.py`)

У групп разные дни занятий (PROG 1 — Пн/Ср/Пт, PROG 2 — Вт/Чт/Сб…), поэтому
группы и студенты считаются **по расписанию именно этого дня**, а не общим
числом активных групп.

* **Расписание дня** — занятия (`Lesson`) с этой датой. Их создаёт генератор
  из недельного расписания (`GroupSchedule`) с учётом переносов и отмен; при
  смене расписания прошедшие занятия остаются как были, поэтому прошлые дни не
  меняются.
* **Состав групп на дату** — `apps.academy.services.student_roster.RosterHistory`:
  группа и статус студента *на тот день* по журналу `StudentStatusEvent`
  (зачисление, перевод, деактивация, пауза).

| Строка | Как считается |
|---|---|
| Групп по расписанию | группы с неотменёнными занятиями в этот день |
| Проведено занятий в группах | из них — где занятие состоялось («Идёт занятие»/«Проведён» или отмечена посещаемость) |
| Студентов по расписанию | уникальные студенты, активные на эту дату и состоящие в этих группах |
| Посетили занятия | уникальные студенты из них с отметкой «Присутствовал»/«Опоздал» хотя бы на одном занятии дня |
| Посещаемость, % | посетили / студенты занятий, которые должны были состояться (отменённые не в знаменателе; сегодня — только уже начавшиеся) |
| Домашние задания, % | как в аналитике LMS: результаты ДЗ, заданного на занятиях этого дня, у студентов, активных на эту дату — сдано (в срок, с опозданием, проверено) / все результаты |

Студент учитывается один раз, даже если в этот день у него несколько занятий.
День без занятий: группы и студенты — 0, посещаемость — «Нет занятий»,
домашние задания — «Нет данных». Сегодняшние занятия учитываются только у
групп, активных сейчас (группа на паузе в план дня не попадает). Календарный
день — по `TIME_ZONE` проекта (Asia/Bishkek); даты занятий — `DateField`,
время запуска переводится в локальную дату через `timezone.localdate`.

## Ежедневные снимки (`DailyPerformanceSnapshot`, `services/snapshots.py`)

Одна строка на дату (уникальный индекс — дубликатов не бывает). Запуск
`capture()` идемпотентен:

1. **Сегодня** — пересчитывается при каждом запуске.
2. **Прошлые предварительные дни** — пересчитываются (посещаемость и ДЗ,
   внесённые с опозданием; ДЗ обычно проверяют на следующем занятии группы).
   Расчёт берёт состав групп и расписание *на тот день*, поэтому сегодняшнее
   состояние в прошлое не попадает. Через `PERFORMANCE_FINALIZE_DELAY_DAYS`
   (по умолчанию 7) день фиксируется (`final`) и больше не пересчитывается.
3. **Пропуски** (планировщик не работал; первый запуск — с 1-го числа
   прошлого месяца) восстанавливаются из записей LMS тем же расчётом.

Сайт читает прошлые дни из снимков; прошедшие дни без снимка показываются
восстановленными из записей LMS (`status: computed`, без записи в базу), а
если в месяце не было ни одного занятия — «Нет данных». Будущие дни и
будущие месяцы — пустая календарная сетка.

Планировщики (достаточно одного):

* Celery Beat — задача `performance.capture_daily_snapshots` каждые 30 минут
  (`CELERY_BEAT_SCHEDULE`);
* Railway Cron — `manage.py run_scheduled_tasks` (шаг `performance_snapshots`).

Вручную и для заполнения более ранней истории:

```bash
python manage.py capture_performance_snapshots --backfill-from 2026-09-01
```

## Ручная корректировка

Только администратор, директор, операционный директор или сотрудник с
Django-правом `performance.change_dailyperformancesnapshot`:

* на сайте (вход сотрудника с правом, не по ключу) — нажать на число дня в таблице;
* `PATCH /api/v1/monthly-performance/snapshots/<ГГГГ-ММ-ДД>/` с полями
  `scheduled_groups`, `held_groups`, `scheduled_students`, `attended_students`,
  `attendance_percent`, `homework_percent`, `comment` (прежние `active_groups`,
  `active_students` тоже принимаются);
* Django admin → «Общая статистика: ежедневные снимки».

Скорректированные поля попадают в `manual_fields`, помечаются «*» в таблице и
автоматическим пересчётом больше не меняются.

## API

Просмотр — любой вошедший активный сотрудник (в том числе бухгалтер и роли с
базовым доступом: префикс открыт в `apps.accounting.access`) или ключ
`X-Dashboard-Key`. Параметры `year`, `month` — по умолчанию текущий месяц;
будущий месяц — пустая сетка (`is_future_month`). В ответе `access` — как открыт доступ (`key` / `user`).

| Запрос | Ответ |
|---|---|
| `GET /api/v1/monthly-performance/` | всё сразу: `days`, `summary`, `trends`, `available_years`, `can_edit` |
| `GET /api/v1/monthly-performance/snapshots/` | показатели по каждому дню месяца (`days`) |
| `GET /api/v1/monthly-performance/summary/` | карточки `attendance_percent`, `homework_percent`, `scheduled_groups` (+ `held_groups`), `scheduled_students` (+ `attended_students`): последний день с данными, предыдущий (для количества — предыдущий учебный день), `change`; для процентов — `month_average` |
| `GET /api/v1/monthly-performance/trends/` | ряды посещаемости, ДЗ, групп и студентов по расписанию (`null` — нет данных; у количества — и дни без занятий) и среднее |
| `PATCH /api/v1/monthly-performance/snapshots/<date>/` | ручная корректировка (см. выше) |

Поля дня: `scheduled_groups`, `held_groups`, `scheduled_students`,
`attended_students`, `expected_students`, `attendance_percent`,
`homework_percent`, `lessons_count`, `held_lessons_count`, `has_data`,
`no_lessons` (+ прежние имена `active_groups`/`active_students` = по
расписанию). Статус дня: `live` (сегодня, на лету), `provisional`, `final`,
`computed` (снимка ещё нет — восстановлено из записей LMS), `missing` (данных
нет), `future`.

## Сайт

Шапка: OKURMENKIDS, «Общая статистика академии», месяц и год, текущие дата и
время; кнопки «Выбрать месяц», «Обновить данные», «Полноэкранный режим»,
«Режим телевизора». Ниже — четыре карточки (с изменением к предыдущему дню),
таблица по всем дням месяца (сегодня выделено, дни без данных — «—» на
штриховке) и четыре графика: посещаемость, выполнение ДЗ, количество студентов,
количество групп. Данные обновляются автоматически каждые 5 минут.

**Режим телевизора** (`?tv=1`): скрывает кнопки, разворачивает страницу на
весь экран, крупные шрифты и карточки, четыре графика в ряд, часы. Рассчитан
на 1920×1080 — вся панель помещается в один экран без прокрутки. Выход — Esc
или «×».

## Миграции и деплой

* `0001_initial` и `0002_dashboardaccesskey` — первая версия (уже применены на
  проде; файлы неизменны). `0003_schedule_based_metrics` переводит снимки на
  показатели по расписанию дня **без потери данных**: старые колонки
  переименованы в `legacy_active_groups`, `legacy_active_students`,
  `legacy_attendance_marked`, `legacy_attendance_attended`, прежние проценты
  скопированы в `legacy_attendance_percent` / `legacy_homework_percent`, ручные
  корректировки перенесены (`active_*` → `scheduled_*`), остальные снимки
  помечены «предварительными» и пересчитываются планировщиком.
* Никогда не переписывать применённую миграцию — только новая миграция.
  (Ошибка «column …scheduled_groups does not exist» на проде возникла именно
  из-за переписанной `0001_initial`: Django считал её применённой и не менял
  таблицу.)
* Веб-сервис Railway при старте выполняет
  `python manage.py migrate_with_lock --noinput` (до gunicorn): на PostgreSQL
  миграции идут под advisory lock — одна реплика применяет, остальные ждут.
* Планировщики не стартуют расчёт, пока миграции не применены:
  `run_scheduled_tasks` — `skipped_migrations`, задача Celery
  `performance.capture_daily_snapshots` — тоже `skipped_migrations`.
